### 11:00 → 11:35 — Keychain Fix: SecAccessControlCreateWithFlags Broken on macOS 26

**Work completed:**
- Diagnosed `patina secrets setup-claude` failure: "A required entitlement isn't present"
- Root cause: `SecAccessControlCreateWithFlags` returns -34018 on macOS 26 (Tahoe) for ad-hoc signed binaries — regardless of which policy is passed
- Wrote Swift test harness (`/tmp/test_keychain.swift`) proving `kSecAttrAccessible` set directly works fine, only the `SecAccessControl` wrapper fails
- Rewrote `store_identity()` in `src/secrets/keychain.rs` to use raw `SecItemAdd` with `kSecAttrAccessible` directly, bypassing `SecAccessControlCreateWithFlags` entirely
- Switched policy from `AlwaysThisDeviceOnly` (deprecated) to `AfterFirstUnlockThisDeviceOnly` (not deprecated, same SSH accessibility)
- Built and installed: `cargo build --release && cargo install --path .`

**Discussion context:**
- User had existing `sk-ant-...` token from `claude setup-token` — just needed vault rebuilt
- Clarified two-vault architecture: global (`~/.patina/`) for cross-project secrets like Claude token, project (`.patina/secrets/`) for per-project team secrets
- User only needs global vault for Claude token injection

**Key decisions:**
- **`AfterFirstUnlockThisDeviceOnly` over `AlwaysThisDeviceOnly`**: not deprecated, available after first login (always true on a Mac that's been used), device-bound, no iCloud sync. Only downside vs Always: requires one login after reboot — acceptable for Mac Studio.
- **Raw `SecItemAdd` over `SecAccessControlCreateWithFlags`**: the `SecAccessControl` API is what's broken on macOS 26 for ad-hoc binaries. Using `kSecAttrAccessible` directly is simpler and works. Declared `kSecAttrAccessible` as extern since `security-framework-sys` doesn't export it.

**Challenges faced:**
- `security-framework-sys` crate doesn't export `kSecAttrAccessible` — had to declare it as `extern "C"` linking to the Security framework
- `core_foundation_sys` not available as direct dep — used `core_foundation::string::CFStringRef` instead
- `CFDictionary::from_CFType_pairs` expects a specific format — needed to zip keys and values into pairs

**Patterns observed:**
- [[use-whats-in-the-tree]] partially violated: `security-framework` crate doesn't expose the raw API we need, had to go around it
- The previous fix ([[commit-1df40fff]]) worked on older macOS but macOS 26 broke it — OS upgrade as silent breaking change
- [[spec-secrets-keychain-ssh]] needs updating: the `AlwaysThisDeviceOnly` decision documented there is now superseded

### 11:43 → 11:55 — Root Cause Reconstruction: MCP Mother Failure Chain

```

  → macOS 26 (Tahoe) rejects SecAccessControlCreateWithFlags for ad-hoc binaries (-34018)
  → store_identity() fails silently (or stored item becomes inaccessible)
  → check_secrets_gate() in src/mcp/server.rs sees: vault exists ✓, identity ✗
  → bail!("Cannot start MCP server")
  → "MCP mother keeps failing ssh AND now local" (not SSH-specific — Keychain broken everywhere)
  → vault manually deleted during debugging to get past the gate
  → all secrets lost (claude-oauth, crates-api)
```

- `check_secrets_gate()` runs before `run_mcp_server()` at line 64

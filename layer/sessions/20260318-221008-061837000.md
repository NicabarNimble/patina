**Discussion context:**

Deep design discussion on sessions and handoffs. Two threads:

**Thread 1 — Why does tmux die?**
- Diagnosed the Mac sleep → lane death mechanism: `launch_adapter_cli` runs the adapter as the direct foreground process in the tmux pane. When the adapter crashes, pane exits → session dies.
- `remain-on-exit on` discussed as a fix — tmux session survives adapter crash, but dismissed: Claude's in-memory conversation is still gone regardless. Keeping the pane alive doesn't solve context loss.
- Per-interface lanes (`derive_interface_session_name`) already implemented in `src/interface/internal/tmux.rs` — each adapter gets its own session name and socket.

**Thread 2 — Session system design rethink**
- Scried [[ref_repo:badlogic/pi-mono]] — their model is **context compaction**: `/compact`, `/autocompact`, auto-trigger when context fills. Patina's current spec explicitly excluded compaction as non-goal.
- [[spec-session-handoff-enrichment]] targets handoff at clean session-end only — doesn't help with crashes (the actual pain point).
- Key realization: **the session system was built around Claude Code's specific logging gap** (logs tool calls + user input, not LLM replies). OpenCode handles context differently and wasn't accounted for in the design.
- Broader reframe: a session = one token context window. The goal = historical chains per interface via `parent_session` linking. Currently `parent_session` exists in `SessionFrontmatter` but is never populated — every session is an orphan.
- **Core design question surfaced**: Patina is a project memory system. It shouldn't be trying to replicate conversation logs — that's each interface's problem. What Patina needs is a **thin, interface-agnostic work period record**: git-tagged, spec-linked, decisions block, handoff block. The conversation log is the interface's concern.
- Patina's Mother/Child/Toy system is the sandboxed operational layer (gather/transform/serve data). Sessions are the memory layer logs of context within token windows, and the session system should serve both human-in-the-loop and future agentic workflows.

**Key decisions:**
- Session design needs a rethink from scratch — not patching [[spec-session-handoff-enrichment]] but reconsidering what a session actually is in a multi-interface world
- The current manual, Claude Code-centric session workflow is broken for multi-interface use
- Interface-agnostic thin artifact (git anchor + spec links + decisions + handoff) is the right shape

**Patterns observed:**
- `[[belief:tmux-lane-defines-active-session]]` is still valid but the handoff side of it is unimplemented
- The ref repos (pi-mono, opencode, claude-code) all solve this differently — no single model to copy directly

- ACP sessions support **conversation replay on load** — full context restored when returning to a session
- Has **session fork** (`session/list`, `session/fork` via ACP)
- Has its own **turn summarization/compaction** (`core: add experimental turn summarization to compact conversation history`)
- This is fundamentally different from Claude Code: in-memory only, lost on restart, no LLM reply logging

**Key insight derived:**
- OpenCode doesn't need Patina to fill a conversation logging gap — it has that natively
- Patina sitting on top of OpenCode as currently designed is mostly redundant for continuity purposes
- What Patina adds for OpenCode is the **project memory layer**: specs in flight, decisions, git anchors — not conversation log replication
- For Claude Code, Patina artifact IS the only continuity mechanism, but it only captures what the agent manually writes — still a partial solution

**Discussion context:**

Requirements discussion for session system redesign — zoomed out to Mother/Child/Toy architecture.

**Session system holistic review:**
Mapped the full stack: git tags (bedrock, durable) → Rust commands (`patina ai session {start,update,note,end}`) → thin shell wrappers (`.claude/bin/`, `.opencode/bin/`, `.gemini/bin/` — one-liners) → skills (agent-driven, fragile) → artifact (YAML frontmatter by Patina, body by agent) → tmux reconciliation (dead lane detection → auto-archive with tmux-lost boilerplate) → env injection (`PATINA_SESSION_ID`, `PATINA_SESSION_ARTIFACT`, `PATINA_AI_INTERFACE`).

Conclusion: Layers 1–3 (git tags, Rust commands, shell wrappers) are solid and interface-agnostic. Layers 4–5 (skills, artifact body) are fragile — agent-driven means crash = empty body.

**Requirements surfaced:**
- `patina ai <interface>` is the single entry point — triggers launch + session logging
- Session artifact = durable, committed, in `layer/sessions/`, uniform format across all interfaces (spec-like design)
- Design output goal first, then build interface modules to produce it
- Session boundary: context window max → explicit exit min
- Exit must be graceful regardless of cause (crash, sleep, explicit, context limit)
- Key challenge: "graceful on crash" requires artifact to be in good state *before* crash, not written at exit

**Mother/Child/Toy dive:**
Reviewed SDK primitives directly:
- `ChildManifest` (`child.toml`): name, type (Connector/Transport/Transform/Lakehouse), runtime, lifecycle, auth
- `GrantedToys`: fetch, lake_names, ingress_sources, connector, query, measure, graph, belief — **no session toy exists yet**
- `pipe/initialize`: the handshake — protocol version + optional auth + optional config
- `spawn_native_with_plan`: resolve binary → load manifest → sandbox → spawn → `pipe/initialize` → `NativeChild`
- Sandbox: `DenyAll` (connector/transport/transform), `ScopedStorage` (lakehouse)
- Mother transport: UDS locally (file perms = auth), TCP + bearer token remotely

**Key architectural proposal:**
A new `ChildType::Interface` (or `ChildType::Session`) — spawned by Mother when `patina ai claude` launches. Handshake via `pipe/initialize` with session_id + artifact_path + project_root. Sandbox = `ScopedStorage` scoped to `layer/sessions/`. `GrantedToys` gains a new `session`/`artifact` toy. SessionChild holds artifact open, writes continuously — durability lives outside Claude's process. Claude crashes → SessionChild still alive → writes handoff, closes cleanly.

**Open questions carried forward:**
- Does Mother have infrastructure to detect that a child's client (interface) has died?
- `GrantedToys` needs a session toy — what shape?
- New `ChildType::Interface` vs reusing existing types?
- Gemini CLI context persistence model still unknown

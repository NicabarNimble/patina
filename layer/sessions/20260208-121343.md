**Discussion context:**
First commit initially used `#[cfg(test)]` to preserve dead functions instead of deleting them. User challenged this as a SPEC divergence — the instructions said "delete dead code" and the AI made a unilateral judgment call to preserve. This led to a substantive discussion about SPECs as mandatory contracts vs optional guidance. The `#[cfg(test)]` half-measure was removed and functions fully deleted.

**Key decisions:**
- **Dead code means dead.** Functions with no runtime callers get deleted, including their tests. Tests exercising dead functions test nothing useful. If the function is needed later, git history preserves it.
- **SPECs are contracts, not suggestions.** When the AI encounters an edge case the SPEC doesn't address, the correct action is to ask — not to make a judgment call. This was formalized as the [[spec-driven-design]] core pattern.
- **Sessions discuss, SPECs decide, code executes.** Clean separation: sessions are the planning/chat layer, SPECs are the authority layer, code implements the authority. This breaks the learning-iteration loop where sessions accumulate knowledge but nothing ships.

**Patterns observed:**
- **The `#[cfg(test)]` anti-pattern is diagnostic.** When you find yourself gating runtime code as test-only to suppress warnings, the code is dead and should be deleted. The gate is a tell that you're avoiding a decision.
- **SPEC divergence compounds.** The initial `#[cfg(test)]` choice was small, but it meant 3 functions and their tests survived as dead weight. Small unilateral decisions accumulate into architectural drift. The fix is structural: SPECs authorize, AI executes.

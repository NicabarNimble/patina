**Key decisions / conclusions:**
- Flue is not “Pi CLI deployed elsewhere”; it is a new harness built on lower Pi libraries. That pattern may be the important architectural clue for Mother.
- Current Mother AI integration is mostly HITL interface orchestration: Mother coordinates envelopes and launches Claude/OpenCode/Gemini/Pi-style guests. This is useful but CLI-level.
- A lower-level Mother design would introduce a Mother-owned `AgentRuntime` contract with implementations such as a Node sidecar using `pi-agent-core`/`pi-ai`, a Flue adapter, and existing CLI guest adapters.
- The safer integration shape is: Mother remains the control-plane authority; the Node sidecar owns the LLM loop; tool calls route back through Mother toys/grants/children rather than receiving unchecked filesystem or secret access.
- This aligns with [[control-plane-authority-distributed-execution]], [[explicit-fail-closed-over-hidden-fallbacks]], and [[adapter-pattern]].

**Challenges faced:**
- The main architectural tension is Rust Mother vs Node-based Pi lower libraries: Mother cannot directly import `pi-agent-core`; a sidecar/protocol boundary is required.
- Another tension is preserving Mother’s capability model. If a Pi-core sidecar gets direct local tools, Mother loses auditability and least-privilege guarantees.
- We avoided treating Deno or WASM as simple drop-in replacements: Deno may wrap or possibly run some npm packages, while WASM/WIT is better understood as the typed capability/plugin boundary.

**Patterns observed:**
- “Pi/Flue lower libraries for agent loop; Mother/WIT/WASM for control-plane and capability isolation” is the promising hybrid.
- CLI tools should become adapters/guests rather than the primary Mother execution abstraction.
- A small spike should prove the seam before re-architecting: `Mother ⇄ Node sidecar ⇄ pi-agent-core/pi-ai`, with sidecar tools calling back into Mother.

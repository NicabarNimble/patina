**Discussion context:**

- User provided detailed session prompt anchoring in core patterns and beliefs before any code. Prescribed a three-phase approach: audit → bible → spec. Read code before write code.
- Walked user through the 6 pillars with concrete module mapping, data flow diagram, and per-pillar tables.
- User's key correction: "THIS IS ALL CORE" — the gray area was a hedge that contradicted the evidence. Mother connects everything (will be plugin manager + UI). Secrets is security infrastructure. Models exist so Patina can work. Scrape is how we get data. Adapters are the entry point.

**Key decisions:**

- **6 pillars not 4** — capture, index, serve, govern were obvious. Connect (mother + adapters + workspace) and protect (secrets + scanner) were initially "supporting infrastructure" but user correctly elevated them. Everything in the binary serves a pillar.
- **Grammars first** — tree-sitter grammars are pure computation with no host imports. De-risks wasmtime integration before tackling the hard problem (WIT host↔plugin communication). If grammar WASM doesn't work, we know before investing in WIT interfaces.
- **Separate crates in monorepo** — plugins are workspace members, not separate repos. They compile to WASM but live next to the code they came from. Separate repos are for community plugins.
- **Feature flags during transition** — compiled-in versions stay behind feature flags during plugin extraction. Zero regression for existing users.
- **Mother manages daemon plugins, PluginHost manages CLI plugins** — different lifecycle: daemon plugins are loaded at startup and stay resident; CLI plugins are loaded on demand.

**Patterns observed:**

- **"Read code before write code" pays off** — the audit found that the MotherChild trait, ForgeReader trait, Oracle trait, and ReleaseStrategy enum already ARE plugin interfaces dispatching to compiled code. The refactor to WIT is mechanical, not architectural. Without the audit, the spec would have invented parallel abstractions.
- **User knows the architecture better than the audit** — the "gray area" was the audit hedging where the user had conviction. Mother's role as the connecting piece and future plugin manager wasn't visible from reading `src/mother/` alone — it required understanding the vision.
- **The bible anchors everything** — every decision in the plugin-system spec references back to [[patina-identity]]. "Is this core?" → check the 6 pillars. "Is this a plugin?" → apply the 4-question test. The bible eliminates ambiguity that the previous 29 frozen specs couldn't.

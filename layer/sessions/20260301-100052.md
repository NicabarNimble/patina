**Completed [[mcp-typed-handlers]] spec → architectural discussion → belief + follow-on spec.**

After completing the typed handlers refactor, explored the deeper question: why do MCP handlers reimplement CLI business logic at all? Ran a detailed structural comparison (3 parallel agents) of MCP vs CLI paths for scry, assay, and spec. Found a spectrum:

- **spec.rs**: pure thin wrapper (zero duplication) — the reference pattern
- **assay.rs**: mixed — 3 query types delegate to `_json()` functions, 7 reimplement SQL inline
- **scry.rs**: full bifurcation — orient/recent/why/detail/use/format_results/log_mcp_query are all parallel implementations of CLI equivalents

**Belief captured:** [[mcp-is-discovery-cli-is-execution]] — refines [[mcp-is-shim-cli-is-product]] with the specific architectural pattern and names spec.rs as reference implementation. Relates to [[bridges-become-permanent]] (explains how bifurcation happened) and [[correctness-by-construction-not-convention]] (thin wrappers make duplication impossible by construction).

**Spec drafted:** [[mcp-thin-handlers]] — 3 phases, 10 steps, 6 exit criteria. Targets collapsing scry.rs from 1,225 to ~200 LOC and assay.rs from 605 to ~150 LOC by creating `_json()` functions in CLI internals and reducing MCP handlers to protocol wrapping only.

**Key discussion:** User raised that MCP was originally intended as a discovery mechanism to teach LLMs about custom CLI commands — not as an execution path. Skills handle workflows, MCP handles tool discovery, CLI handles execution. The bifurcation happened because `_json()` functions didn't exist when MCP was built.

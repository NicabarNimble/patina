### 23:06–00:15 - Mother-Child-Toy architecture deep dive

Explored the capability-based architecture across two evolutionary stages:

**Stage 1: Pipe-based process model (ducklake v1)**
- Read codebase: `crates/patina-pipe-types/src/config.rs`, `crates/patina-pipe/src/http_proxy.rs`, `children/ducklake/src/main.rs`, `src/broker/mod.rs`
- Mapped beliefs: [[children-have-agency-toys-are-capabilities]], [[initialize-is-capability-grant]], [[connector-toy-is-indivisible-authority]], [[no-untyped-blobs-at-trust-boundaries]]
- Produced comparison analysis against 8 capability systems: OCap theory, Capsicum (FreeBSD), Chromium sandbox, WASI Component Model, Plan 9 namespaces, Erlang/OTP, Android (counterexample), Deno

**Stage 2: Fuchsia/Zircon deep comparison**
- Researched Zircon kernel capability model: handles, rights bitmasks, bootstrap channels, `zx_process_start()`
- Researched Fuchsia Component Framework: `use`/`offer`/`expose` manifest declarations, capability routing
- Identified closest parallels: Zircon bootstrap channel ≈ `pipe/initialize`, Component Manager `offer` ≈ Mother grant construction
- Key insight: Fuchsia's two-layer design (kernel capabilities + framework routing) suggests Patina may benefit from separating capability definition (manifest) from enforcement (runtime proxy) as child types grow

**Stage 3: Knowledge-child platform review ([[knowledge-child-platform]])**
- Full code review of WASM-first evolution: `src/plugin/internal/knowledge_child.rs`, `src/mother/state.rs`, `src/commands/mother/registry.rs`, `src/commands/mother/daemon.rs`, `src/mother/child.rs`
- SDK review: `crates/patina-toy-sdk/src/lib.rs`, `crates/patina-child-sdk/src/lib.rs`
- Proof children: `plugins/ducklake/src/lib.rs`, `plugins/belief-verifier/src/lib.rs`
- Assessed against three review questions:
  1. Legacy `mother-child` isolated via `RegisteredChild::Legacy` vs `::Knowledge` enum — quarantined structurally
  2. Capabilities double-enforced: manifest load-time validation + per-call grant checks on every host import
  3. Both proof children demonstrate real agency — DuckLake drives fetch→store→cursor workflow via toys; belief-verifier drives event→classify→verify→ack via toys
- Noted: `PhantomData<B>` backend pattern in toy-sdk is elegant for backend-agnostic toy authoring
- Noted: `KnowledgeRuntimeStore::open()` creates new SQLite connection per operation — potential bottleneck under frequent heartbeats
- Noted: `TaskIntentKind` enum duplicated 3× across mother/child.rs, toy-sdk, and WIT bindings — manageable at 8 variants but scaling risk
- Noted: WASM DuckLake uses `host_http` domain gating but loses fine-grained `ConnectorToy` proxy enforcement (allowlist + credential injection + leak detection) from pipe model

**Architectural positioning:**
- Patina's closest relatives: WASI (typed capability imports, fail-closed) and Capsicum (irreversible capability restriction)
- Distinctive contribution: domain-level indivisible capability bundles (credential + policy + scope as atomic unit)
- Evolution from pipe→WASM moves enforcement from HTTP proxy to host function gating — closer to Zircon's handle-based model

### Key findings
- The knowledge-child platform is a real platform upgrade, not cosmetic
- Spec [[knowledge-child-platform]] exit criteria are met across all 9 checks
- The SDK teaches the correct mental model: children use typed toy bundles, not host RPC bags
- Mother authority / child agency separation is preserved through the architectural transition

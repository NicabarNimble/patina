**Discussion: Mother graph architecture rethink**

User observed that our FTS5 knowledge search in mother duplicated assay's mechanism
at cross-project scope while ignoring mother's actual value: the **graph**. This
triggered a fundamental rethink of mother's role.

Key realizations (collaborative, user-driven):
1. Mother's CLAUDE.md says "graph **routing**" — not searching. We built search.
2. The four layers have clear jobs: assay (structural + FTS5), scry (semantic),
   graph (relationships). FTS5 in mother duplicates assay.
3. Graph should map **beliefs as first-class nodes**, not just projects.
   Edges: SUPPORTS, ATTACKS, APPLIED_IN, ORIGINATED_IN, EVOLVES_FROM.
4. Human-in-the-loop for all cross-project decisions: adoption, promotion to core,
   belief import. LLM does ingestion, human organizes.

**Academic grounding discovered:**
- [[Dung-argumentation-framework]] (1995): supports/attacks graph — our belief
  relationships are literally this
- [[Gärdenfors-epistemic-entrenchment]] (1988): ranking beliefs by centrality —
  our entrenchment levels (low → medium → high → very-high)
- [[IBIS]] (Kunz & Rittel 1970): design rationale capture during work — our
  session-based belief creation

**Architecture aligned with outside agent (passive-operational-memory-ledger):**
- Beliefs stay in each project's `layer/surface/epistemic/beliefs/` (sovereignty)
- `patina belief import --from <project> <belief-id>` for human-driven adoption
  with provenance tracking + entrenchment reset to low
- Mother graph sync reads richer data from patina.db (currently only 5 of 33 columns)
- New edge tables in graph.db for belief-to-belief relationships across projects
- `mother graph query` subcommands for belief-aware graph traversal
- Promotion to core is a human decision, metrics-informed but not automated
- Assay/scry stay project-scoped, unchanged

**Existing infrastructure audit:**
- Scraper already parses `## Supports`, `## Attacks`, `## Attacked-By`, `## Evidence`,
  `## Applied-In`, `## Verification` — all the relationship data exists in patina.db
- Mother graph already has nodes, edges, weight learning, usage tracking
- The heavy lifting is already done. The work is: richer sync (more columns + edges),
  new `belief import` subcommand, new `mother graph query` for belief traversal
- Estimated: small changes to existing commands, not a rewrite

**Key decisions:**
- [[design-gaps-are-specs-not-bugs]] applied: the per-source rebuild was a design gap,
  not a bug. This architecture rethink is being captured as discussion first, spec next.
- No `portable` tag or auto-promotion. Human decides what crosses projects.
- No NDJSON serialization layer. Keep current model: scraper writes local DB,
  mother reads local DB directly.
- Core markdown files (`dependable-rust.md`, etc.) predate belief system but could
  gain belief metadata. Content stays unchanged.

**Patterns observed:**
- User's instinct ("this doesn't feel right architecturally") was correct even before
  being able to articulate why. The conversation needed collaborative back-and-forth
  to surface the real issue: FTS5 in mother = wrong layer doing wrong job.
- Outside agent (other project) contributed a solid first proposal. Critique + iteration
  produced a much tighter architecture in two rounds.
- The existing codebase has more infrastructure than either of us realized. The audit
  revealed the scraper already parses everything we need — the gap is in sync, not parsing.

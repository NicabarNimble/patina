## Decisions
- wit-deps-wasi-alignment scope narrowed: WASI P2 multi-file packages only, Patina extensions untouched
- Spike proved wasi:io works as multi-file directory in deps/ — both bindgen macros resolve correctly
- `deps/` is hardcoded in wit-parser (line 399 of resolve.rs) — can't point bindgen elsewhere
- wasmtime itself uses flattened deps per-crate (same approach as Patina); newer crates (keyvalue, config, tls) use multi-file directories — BA is moving in the direction we want
- Each crate carries its own deps — self-contained parts. Copies across crates are the cost of self-contained parts, not a bug.
- Two-way toy split: adopted WASI P2 (use upstream as-is) vs everything else (ours, aligned to BA patterns)
- Children are components. Toys are WIT interfaces. Pandos are compositions. Mother is the virtual platform layer.
- Path 2 (direct child-to-child WIT composition via wasm-tools compose) preferred over path 1 (Mother as typed mediator)
- handle(string,string) is the fat child phase. Typed WIT exports are the decomposed phase. System supports both.
- Data type packages (e.g. record types) are toys — same package, export side. Not a separate concept.

- wit-parser source: `let deps = path.join("deps");` — hardcoded, no config option

- wasm-tools component wit on schema-enforcer.wasm shows: imports all toys + WASI plumbing, exports generic handle/tick/drain — the typed export gap is visible

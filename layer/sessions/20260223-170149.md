**Phase 3 — Queue System (1 new command + 2 enhancements):** Implemented `patina spec next [--json]` — ranks all specs by priority (active > blocked-ready-to-resume > paused-with-age > ready > draft), uses impact as tiebreaker within tiers, outputs recommendation with reasoning. **Deviation analysis:** 6 deviations total across Phase 2 (4) and Phase 3 (2). All deliberate refinements: `--description` flag instead of interactive prompt (composability), `--new-id` instead of `--id` (avoids ambiguity with positional arg), no `--major` on split (edge case), added Recovery section (additive), impact as tiebreaker not separate tier (more useful), JSON contract unchanged (stability). Documented inline in SPEC.md following Phase 1 pattern.

**Key decisions:**
- **`with_yaml_rollback()` is generic `<T>`** — returns whatever the action closure returns. Both current callers return `()` but the function is reusable for future commands that need a value back.
- **`split_spec()` duplicates completion logic** rather than calling `complete_spec()` — `complete_spec()` does its own find+validate+output that would conflict with split's flow. Same pattern as `complete_spec()` vs `mutate_spec()` (deviation 2 from Phase 1).
- **`load_dep_counts()` extracted as shared function** — used by both `next_spec()` and `show_ready_specs()` to avoid duplicate DB queries.
- **`spec_age_days_from_list()` re-reads the file** on each call to get `paused_date`/`blocked_date` from frontmatter. `SpecInfo` doesn't carry date fields — could optimize later but N is small (number of specs).

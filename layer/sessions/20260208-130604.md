**Discussion context:**

The SPEC said "facts first, then meaning for gaps" which directly maps to: call assay → collect source_ids → call scry → filter out already-seen ids → output both sections. No tuning parameters needed. The key insight from the SPEC's Phase 3 design (line ~214) was that fusion should happen at the consumer level (context command), not inside either search system — this keeps scry and assay independent per [[unix-philosophy]].

**Key decisions:**
- **No-topic case unchanged.** Without a topic, assay and scry would return random/irrelevant results. Only topic-filtered context gets the fusion section. This aligns with context's purpose as CLAUDE.md generation — without a topic, you get full project context; with a topic, you get focused context using both search systems.
- **5 results per signal.** Kept limits small (5 factual + 5 semantic) to avoid overwhelming context output. The LLM can always call scry or assay directly for deeper exploration.
- **QueryEngine created per-call.** In the MCP server, the engine is initialized at startup. In context, we create it when needed. Acceptable overhead for a context query — `SemanticOracle::new()` only checks file paths, actual index loading is lazy in `query()`.
- **MCP descriptions as documentation.** Updated scry/context/assay descriptions to accurately reflect what each tool does post-split. These descriptions are the primary guidance for LLMs choosing which tool to call.

**Design discussion: Data lakes, personas, and Patina's identity**

Extended architecture session tracing the path from "how do data lakes work" to "what IS Patina." Explored through the lens of the existing Google Workspace project at `/Users/nicabar/Projects/Patina/passive-operational-memory-ledger` and how it connects to Patina.

**Key design evolution (chronological):**

1. **Three concentric rings** — core (belief system), actionability (WASM plugins), feeding (data lakes). Started here.

2. **Three-layer external data model** — Lake (raw, complete, Mother-managed) → Projection (scoped, normalized, project-configured) → Consumption (Patina's existing data stack). Mapped forge as existing precedent.

3. **Fetch / Scrape / Schedule separation** — three distinct plugin roles. Fetch gets data from source. Scrape normalizes it (plugin-dispatched like grammars). Schedule (mother-child) manages lifecycle. Forge currently tangles all three.

4. **Catalog over normalization** — don't normalize upfront when you don't know what's needed. Index metadata first (cheap, everything), pull content selectively per project. ELT pattern.

5. **Patina is the workshop, not the product** — initial framing. Projects built with Patina have their own RAG/pipelines. Patina helps build them.

6. **Reframe: Patina IS the product too** — [[patina-is-domain-agnostic-knowledge-system]]. A production system monitoring a data lake IS a Patina instance. Same engine, different plugins. "Build with Patina, deploy AS Patina."

7. **Persona is a Patina instance** — [[persona-is-a-patina-instance]]. Not a filter within one system but a full sovereign instance. Mother federates across personas.

8. **Persona linking and streams** — admin-controlled connections between personas. Knowledge flows bidirectionally through Mother. Public/private/shared visibility levels.

9. **Phasing** — (1) flush out plugin system + scrape dispatch, (2) extract forge/spec/sessions from core, (3) Mother personas and federation.

**Key decisions:**
- No design doc / report (user explicitly rejected — "trap of dead docs land")
- Schemas live with plugins, not in Patina core
- Lake catalog is metadata-only index, not full normalization
- `patina scrape` becomes plugin dispatch (like grammar dispatch today)
- Mother lake registry extends existing ref repo registry pattern
- Persona UID managed by Mother, `persona:` field on beliefs becomes provenance marker

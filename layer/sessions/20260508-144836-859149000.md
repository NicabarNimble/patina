**Discussion context:**
- The conversation clarified that the goal is not a dashboard like Atlas, but a Mother-managed visualization substrate: the user asks an agent for a view, the agent selects/adapts Allium view metadata, Mother manifests a live buffer over existing data, and renderers connect to buffers.
- We leaned into Emacs design directly instead of generic UI terms: buffers live outside sessions, windows connect/disconnect, frames are renderer clients, and major/minor modes describe display behavior.
- We framed Allium as “agents as Lisp”: editable structured behavior that agents can modify, but constrained by observed data, local metadata, and reversible history. Captured as [[allium-as-agent-display-lisp]].

**Key decisions:**

- SvelteKit is a future frame/renderer, not the owner of buffers.
- Buffers display existing observed/catalogued data only. Missing required data creates an observability gap; no view is opened and no data is invented.
- The first implementation slice uses a built-in Mother status proof shape rather than a full Allium compiler, preserving scope while proving the contract.

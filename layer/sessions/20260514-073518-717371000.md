**Discussion context:**
- User framed the 1075 session files as a longitudinal dataset of working with LLMs over time, to anchor a peer-reviewed paper and an online project on the evolution of human–LLM collaboration.
- Iterated through research-design and architectural questions:
  - Source-of-truth (patina) vs. derived dataset (separate research repo); copy + freeze, never move.
  - Reproducibility / proof provability anchored in git content addressing — patina commit SHAs plus per-file content hashes as lineage.
  - Wikilink portability across repos — resolve at ingestion into a denormalized table; preserve original `[[X]]` tokens verbatim, never rewrite source artifacts.
  - SQL projection in DuckDB over immutable session artifacts.
  - Temporal grain: per-file-touching-commit observation rows, with `observed_at_patina_commit` as part of the lineage.
  - Continuous (not snapshot) ingestion — research repo follows patina; paper citations resolved via tagged DuckDB release artifacts attached to GitHub.
  - "Outside-looking-in" posture: research repo consumes patina's own tools (Scry, Assay, Oxidize, Scrape, tree-sitter grammars) as external consumers — doubles as a real-world validation workload for those tools on a non-patina-internal use case.
- Reality-checked the operational scraper and surfaced concrete gaps that justify a separate research-grade extractor rather than extending the existing one in place.

**Key decisions:**
- Research project lives in a separate repo with its own DuckDB; never writes back to patina. Patina mutability is observed (via `git log -- layer/sessions/<file>`), not caused.
- Temporal model is v1, not deferred — every fact carries a `(source_file_sha256, patina_commit, pipeline_version)` lineage triple from day one.
- Gaps are first-class rows in a dedicated table (missing `llm`, missing end_tag, empty Previous Session Context, commits in range not referenced), not silent NULLs. Makes "60% of Claude sessions had no narrative body" a real query, not an interpretation.
- Wikilink resolution is denormalization, not rewriting — `link_tokens` preserves verbatim text, `link_resolutions` stores resolved metadata (full SHA, GitHub URL, commit/artifact provenance).
- v0 scope deliberately small: extract everything the operational scraper misses → `research.duckdb` → one canonical query end-to-end. Defer patina-tool integration (Scry/Assay/Oxidize invocation), external PI/OpenCode logs, and anonymization pipeline to later milestones.
- Sibling-research-scraper preferred over extending the operational scraper in place; operational and research extraction should evolve on independent cadences.

**Challenges faced:**
- Operational `scrape layer/sessions` drops the `llm` field entirely from its `SessionYaml` struct — *the* primary axis for any analysis that distinguishes interfaces (Claude vs. PI vs. OpenCode). Several other frontmatter fields are parsed-but-not-stored (`status`, `interface`, `participants`, `updated`) or not parsed at all (`git.starting_commit`, `git.start_tag`, `git.end_tag`).
- No wikilink extraction in the current scraper; the whole knowledge-graph dimension is invisible to operational analytics.
- `Work Completed` regex matches numbered lists only (`^\d+\.`); current bullet-list session bodies are systematically undercounted as `session.work` events.
- Re-scrape is DELETE+INSERT; no history of how a session mutated over time. Doesn't support the continuous/temporal observation model the research project needs.
- Voice-input transcription created tool-name ambiguity (Scry confirmed; "say"→Assay, "oxidation"→Oxidize/Scribe). Confirming proper nouns before designing prevented downstream drift.

**Patterns observed:**
- The 1075-file corpus already contains most of the comparative axes the paper needs (interface, llm, participants, git linkage, branch, commit message taxonomy) — analytical capability is bounded more by extraction completeness than by re-instrumentation.
- Operational tooling and research-grade extraction are fundamentally different consumers of the same source; entangling them in a single scraper would force the operational schema to carry research-only columns and would couple release cadences. Sibling consumers over a stable read-only source is the cleaner shape.
- Using patina's own tools (Scry, Assay, Oxidize, Scrape, tree-sitter children) as external consumers turns the research project into a real-world test bed for those tools. The methodological section of the paper writes itself.
- Empty Claude template vs. dense PI distilled-log narrative is itself a measurable interface-quality regime difference. The dataset can surface it as a finding rather than as an editorial observation.

**Beliefs captured this session:**
- [[observational-research-is-read-only]] — observational projects studying a source must never write back; source mutability is observable signal, not contamination.
- [[gaps-are-first-class-data]] — missing data belongs in explicit rows with type/source/detector, not in silent NULLs.
- [[study-with-your-own-tools]] — research projects studying their own toolchain should consume it as external users; the study doubles as real-world tool validation.

**Open decisions blocking v0 scaffold:**
- Repo name (candidates surfaced: `patina-evolution`, `assayed`, `llm-coevolution`, `session-observatory`).
- Language for v0 (Python for exploratory speed vs. Rust for toolchain alignment; recommendation: Python for v0, Rust for production pipeline once schema stabilizes — itself a Rust-vs-Python data point for the paper).
- Public/private repo posture from day one.

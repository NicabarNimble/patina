### 11:30 - Synthesis: skills and sessions are the same problem rotated 180°

The two design problems are symmetric:

| | Skills | Sessions |
|---|---|---|
| **Today** | One intent → N hand-written interface formats | N native conversation logs → ignored, replaced by one hand-edited markdown |
| **Should be** | One canonical → transformed → N interface formats (publish) | N native logs → ingested → one curated summary (subscribe) |
| **Direction** | **Define once, fan out** | **Capture from N, summarize once** |

Both are about: *the interface should not be the unit of authorship*. For skills, the interface is a publishing target. For sessions, the interface is a capture source. In both cases the canonical thing belongs in the project, not in the interface dir.

The current architecture got this backwards on both axes because it grew up around Claude Code: Claude couldn't give us conversation logs cleanly, so we made the user author a markdown summary instead — and then we treated that approach as universal. Same shape with skills: Claude shipped first, we wrote markdown skills for it, then we wrote them again for opencode and gemini.

The summarizer (the thing that turns N raw logs into a curated session summary) **wants to be a skill**. So the skill repo and the session redesign want each other.

### 11:45 - Proposed shape (mother repo for skills)

A canonical skill should be:
1. **Located somewhere project-canonical** — candidates: `layer/skills/`, `sdk/skills/`, or `sdk/{domain}/skills/` per-domain plus `layer/skills/` for cross-cutting Patina-meta skills (session, spec, beliefs, review). `sdk/ba/skills/` from [[spec-ba-truths]] becomes an instance of the per-domain pattern.
2. **Format = the union of what every target needs.** Claude's MD + YAML frontmatter (`name`, `description`, body) is richest; Gemini's `prompt` field is just the body; OpenCode is plain markdown. Canonical = MD + YAML frontmatter; transformers strip frontmatter or wrap in TOML.
3. **Published by `patina ai setup` (or new `patina skill publish`).** Each `InterfaceProvider` gains a `publish_skill(canonical, dest)` method. The match-statement registry becomes a per-interface transformer.
4. **Trackable by Patina** — `patina skill list`, `patina skill show <name>`, with `.patina-managed.toml` per interface declaring installed canonicals + version.

The seam is clean: `InterfaceProvider::get_custom_commands` already returns `Vec<(name, content)>`. Today the content is hardcoded markdown specific to the interface. Tomorrow it's the result of running canonical skills through an interface-specific transformer.

### 11:50 - Proposed shape (session redesign)

Two honest options surfaced:

- **Option A — Lifecycle stays, log added underneath.** The markdown in `layer/sessions/` is still authored, but as a *summary over* a raw log captured at `layer/sessions/.logs/{file_id}.jsonl`. Frontmatter gains `raw_log_path`. `/session-end` triggers a summarization pass. Mother still tracks lifecycle. Git tags still bracket. The user-visible workflow doesn't change much, but the *truth* moves from the markdown to the log.

- **Option B — Ambient capture, intent markers optional.** Interfaces capture their own logs (they already do). New `patina session ingest <interface> <log_path>` reads native logs, extracts boundaries, produces summary, tags Git retroactively. `/session-start` becomes optional intent annotation. More invasive but matches reality better — the conversation happens whether or not Patina knows about it.

Open trade-off: Option B breaks the "explicit goal at session start" pattern that has been quietly valuable for forcing intention. Hybrid likely correct: ambient capture + optional intent markers.

Either way, the redesign needs:
1. **Per-interface log discovery** — where does each interface natively write its conversation log? Not yet known for opencode/gemini, partially for claude. First exit criterion of any session redesign spec.
2. **A `LogCapture` capability on the interface trait** — `locate_conversation_log(session_id) -> Option<PathBuf>` and `parse_log(path) -> Result<Vec<Turn>>`.
3. **A summarizer** — implemented as a canonical skill (`summarize-session.md`) invoked at end-of-session.

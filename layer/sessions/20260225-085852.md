**Work completed:**
- **[[spec-metadata-mutations]]** (v0.31.7): Added `patina spec set <id> <field> <value>` CLI command + `spec.set` MCP tool. Supports 4 fields: `beliefs`, `related`, `references` (Vec — `+`/`-` prefix for add/remove) and `target` (scalar — set directly, empty clears). Each mutation writes YAML, updates DB, creates git commit.
- Implementation: `set_spec_value()` + `set_spec()` in `mutations.rs`, small `apply_list_mutation()` helper for Vec fields, `Set` variant added to `MutationDetail` enum and `SpecCommands` enum. Followed [[promote_spec_value]] as the simplest existing mutation pattern.

**Key decisions:**
- Deferred `milestones` and `schemas` fields per SPEC — they have nested object structure requiring different handling
- Used `allow_hyphen_values = true` on clap arg to allow `-value` syntax for remove operations (clap interprets `-` as flag prefix otherwise)
- Deferred `set_spec_value` re-exports to commit 2 (MCP wiring) to keep commit 1 warning-free

**Challenges faced:**
- Clap flag collision: `patina spec set my-spec beliefs -old-belief` failed because clap parsed `-o` as a flag. Fixed with `#[arg(allow_hyphen_values = true)]` — caught immediately during live testing
- Rustfmt disagreements on multi-line chains and error response formatting — caught by pre-push checks

**Patterns observed:**
- Read-all-code-first approach paid off: zero design pivots, implementation matched SPEC exactly
- The `load_and_mutate()` + `git_stage_and_commit()` pattern is highly composable — adding a new mutation is ~100 lines following `promote_spec_value` as template
- Live testing against the spec's own SPEC.md file (adding/removing beliefs on `spec-metadata-mutations`) was both dogfooding and verification

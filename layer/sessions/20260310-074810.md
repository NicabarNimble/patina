- Drafted [[ducklake]] through 4 major revisions:
  1. v1: Mother routes pre-fetched records to passive DuckLake child
  2. v2: Mother as router, child stores — but Mother still orchestrates fetch cycle
  3. v3: Child is autonomous — drives its own connectors, handles partial failures, per-type cursors
  4. v4: Error escalation model — child handles data flow, escalates auth to Mother
- Drafted [[http-proxy-extraction]] — extract `build_production_handler` from `broker/http.rs` to `patina-pipe` so children can proxy connector HTTP with same security (domain allowlist, credential injection, leak detection)
- Drafted [[measure-process-owned]] — shared vocabulary (5 verbs, tool/mode/source), local storage per process, Mother queries on demand
- Created belief [[telemetry-is-process-owned]]

**Key decisions:**
- DuckLake child is autonomous: spawns its own connector, drives fetch cycle, handles partial failures. Mother hands off and gets out of the way. This is a bigger child model than anything in the existing architecture.
- No lake tables in graph.db. DuckLake catalog IS the registry. Mother just tracks name + path in a lake.toml file.
- Per-type cursors live inside DuckLake catalog (`_sync_cursors` table). If you move the lake, cursors come with it.
- HTTP proxy extraction uses feature-gated reqwest in patina-pipe. Acknowledges patina-pipe is "broker substrate" not just wire protocol.
- `tool` vs `source`: tool = WHAT measured (controlled vocabulary), source = WHO emitted (process identity). Children cannot invent tool names.
- Proxy enforces policy, does NOT emit telemetry. Callers own their own observability.
- http-proxy-extraction and measure-process-owned are parallel dependencies; ducklake needs both.

**Outside agent audit feedback incorporated:**
- Cargo feature flag caveat (additive, not strong isolation)
- ChildConnection in harness.rs must be promoted to production API
- Measurement is caller's concern, not proxy's
- Exhaustive mapping tests for AuthPlan → HttpProxyConfig
- ProxyInjection::None renamed to InProcess
- Canonical event envelope with schema_version for forward compat
- Mother retrieval via direct store read (works when child isn't running)

**Patterns observed:**
- Spec evolution through conversation: 4 revisions of ducklake, each time the child became more autonomous. The user's mental model was ahead of the spec — spec had to catch up.
- "What goes in the child?" is the core architecture question. Answer: everything the child needs to be self-contained. Mother provides resources at setup, then gets out of the way.
- DuckLake (the extension) eliminates enormous amounts of custom code: Parquet writing, layout, compaction, schema evolution, dedup. One dependency replaces the entire custom lakehouse child from raw-lake-ingestion.

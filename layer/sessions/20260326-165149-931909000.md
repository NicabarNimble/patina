**Work completed:**

1. **Greenfield child architecture rethink** — Examined all 7 production children and discovered they're all `kind = "knowledge-child"`, `role = "app"`, and most are decorative stubs (spec-manager, lake-manager, doctor count dispatches while Mother calls core library code). Only ducklake does real work through toys.

2. **Discovered current "children" are fakes** — Traced the spec-manager dispatch path: CLI → Mother HTTP → `builtin_spec_dispatch()` → `patina::spec::execute_command_value()` (core Rust library). The WASM child increments a counter. It doesn't own any spec logic. Same pattern for lake-manager and doctor.

3. **Lake deep dive** — Lakes are DuckDB files (`lake.duckdb`), not Parquet as beliefs claimed ([[raw-lake-is-capture-contract-first]], [[mother-owns-destination-format]]). Lake-manager is `mkdir` + `touch lake.toml`. Ducklake doesn't use lake-manager — it talks to lakes directly through the `store` toy. Lake-manager as a separate child adds nothing.

4. **Ducklake role smearing identified** — Current ducklake child both fetches from GitHub AND stores into DuckDB. This violates [[connectors-never-materialize]] and [[mother-owns-destination-format]]. Clean split: github child (connect kind) produces records, ducklake child (store kind) accepts and stores them, Mother routes between them.

5. **New child kind taxonomy** — Kind should reflect job shape in the data plane, not WIT world:
   - **connect** — talk to external systems, produce records (github, gmail, s3, jira)
   - **transform** — process data, input→output (grammars, LLM chunkers, parsers)
   - **store** — accept records, persist, answer queries (ducklake, parquet-writer)
   - **move** — orchestrate data flow between sources and destinations

   Multiple kinds share one WIT world (worker). Pure-compute transforms use the compute world (current pipeline). Kind determines SDK developer experience, not sandbox shape.

6. **SDK vision: agent-legible child factory** — The SDK's real user is an LLM agent (Claude, GPT, any agent), not a human developer reading docs. A user says "I need Salesforce data in Patina." Their agent reads the SDK, picks a template, generates a working child. The SDK must be:
   - One trait per kind with obvious names
   - One right way to do each thing
   - Templates that work out of the box
   - Code IS the documentation, types ARE the contract

7. **Guest surface projection** — Children declare actions with typed inputs/outputs. Mother projects those onto ALL guest surfaces automatically (CLI, MCP, HTTP, agent). The child never decides "I'm CLI only" or "I'm MCP only." The child is logic. Mother is the surface. `patina s3 list-buckets` (CLI) and `s3_list_buckets()` (MCP tool) and `POST /api/s3/list-buckets` (HTTP) all hit the same child action.

8. **Agent architecture** — Agents can be WASM children with a `reason` toy (LLM access through Mother) and a `delegate` toy (call other children through Mother). Mother controls LLM budget, rate limits, model selection, and audits every reasoning call. Alternatively, agents are persistent guests with long-lived sessions. Both models work. Three worlds: **worker** (toys+daemon), **compute** (pure function), **agent** (reason+delegate).

9. **Patina's competitive position clarified** — Patina is a knowledge protocol with a composable data plane. Any agent can extend it. Not locked to any LLM vendor. The protocol is the constant. Agents come and go. Children are the portable, sandboxed, agent-generated extensions.

**Key decisions (this period):**

- **child-command-surface is the wrong next spec.** CLI commands are a guest surface concern, not a child concern. Mother should project child actions onto CLI, not children owning CLI surfaces.
- **Kind reflects job shape, not WIT world.** connect/transform/store/move as kinds, sharing worker and compute worlds.
- **SDK is a child factory for LLM agents.** Pick kind → implement trait → ship. The agent generates the child from the SDK surface.
- **Three worlds, many kinds, one Mother.** Worker (data children with toys), compute (pure transforms), agent (reasoning children).
- **Children are data workers in the belief system ecosystem.** They connect, transform, store, move data. They extend Patina's ability to interact with the world. Apps and agents are guests, not children. Exception: agent children sandboxed with `reason` toy.

**Beliefs created this period:**

- [[retire-before-building]] — Retire dead abstractions before building new ones in the same namespace.
- [[anchored-beliefs-decay-faster]] — Beliefs referencing file paths/type names decay faster than principle-level beliefs.

### 22:53 - Final Update (covering since 22:30)

**No new commits.** Final discussion segment: SDK ergonomics direction.

**Work completed:**

1. **SDK audit** — Mapped all 4 SDK crates (~2,600 lines total). Identified that the existing `KnowledgeChild` trait, `granted` module, toy backend traits, and tier crates (core/data/agent) are solid and should stay. The pain points are manual toy wiring, 8-method trait with 5 stub defaults, and string-typed `handle(action, payload)` dispatch.

2. **Ctx design** — Identified `Ctx` as Patina's equivalent of Cloudflare Workers' `env`. `Ctx` wraps granted toys, is assembled by macros from `[needs].toys` in `child.toml`, and is passed to kind-specific handler functions. Stack: developer writes `fn fetch(ctx: &Ctx)` → `Ctx` wraps `granted::*` → granted wraps WIT host imports → WASM sandbox enforces → declared in `child.toml`.

3. **Implementation strategy: layer, don't rewrite.** Kind-specific traits (`ConnectChild`, `TransformChild`, `StoreChild`) generate `KnowledgeChild` impls via macros. No WIT changes, no world changes, no Mother changes. Follows [[compat-seam-before-rewire]] — `KnowledgeChild` is the seam, kind traits build on top.

4. **Transform discussion** — Grammars (current pipeline children) are transforms. `kind = "transform"` covers both pure-compute (pipeline world, zero toys) and toy-using transforms (worker world). SDK picks world based on whether toys are declared. Developer never thinks about worlds.

5. **Lake/Block architecture sketched** — Lakes are raw captured data (append-only, as-observed). Blocks are derived structured data (rebuilt by transform children). Connect children → lakes. Transform children → blocks from lakes. Store children manage the storage.

6. **Next step identified** — SDK ergonomics spec: add `Ctx` struct, kind-specific traits, registration macros. Additive layer on existing SDK. No blast radius.

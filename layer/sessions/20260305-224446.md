### 23:15 - Track 1: Pipes vs Plugins
Walked through three-layer model with concrete examples (GitHub, Slack, RSS, Google Workspace). For each: WASM need, connection model, auth model, data types. Compared with actual plugins (doctor, repos, models, forge). Clear pattern: plugins have opinions (query, measure, toys), pipes just move data (http, emit). Gray areas identified: PR reviewer uses pipe data but adds plugin behavior. **User confirmed: PR reviewer is a plugin that uses github pipe. Slackbot uses slack pipe.**

### 23:30 - Track 2: Why WASM for Pipes?
Traced security model through `host_support.rs` — domain allowlist, credential injection, leak detection all host-side. WASM just prevents bypass. **User challenged: "how could we use WIT and not WASM and make pipes safe?"**

### 23:45 - Key Insight: Host-Proxied I/O IS the Security Model
Discovered that all security is in the host, not in WASM. Proposed process-based pipes over stdio (like MCP). Pipe asks host to make HTTP calls. Three-layer security: (1) protocol enforcement, (2) capability manifest, (3) OS sandbox (macOS sandbox-exec, Linux Landlock — same as Chrome renderer processes, Docker containers). **User confirmed: WASM for plugins, process-based for pipes.**

### 00:00 - stdio vs Alternatives
Compared stdio, Unix domain sockets, TCP, shared memory. stdio wins: cross-platform, sandbox-safe, MCP-compatible, low complexity. Unix socket as future escape hatch for bidirectional streaming.

### 00:15 - MCP Transport Analysis (Track 3)
Analyzed why MCP has three transports (stdio, HTTP+SSE, Streamable HTTP): deployment topology. Same reasoning maps to pipes: local (stdio), remote VPS (HTTP+SSE), shared multi-Mother (Streamable HTTP). **Key question: should pipe protocol just BE MCP?** Pipe as MCP server, Mother as MCP client.

### 00:30 - Crypto Patterns for Pipe Safety
User asked: "hasn't crypto solved some of these pipe questions?" Mapped relevant patterns: UCAN capability tokens (scoped delegation, not raw credentials), content-addressed facts (IPFS/IPLD provenance), CRDTs + Iroh (multi-pipe convergence), zero-knowledge (credential verification). Practical timeline: host-proxied I/O now, UCAN when auth ships, content addressing when multi-destination, CRDTs when data lakes sync.

### 00:45 - P2P Node Architecture (Track 4)
User asked how pipes work in a p2p network. Traced EVM node analogy: every node is sovereign, state syncs via gossip, no node is "the server." Mapped to Patina: each node runs pipes locally, facts sync via Iroh documents, content-addressed dedup. Node specialization: pipe nodes, compute nodes, belief nodes, leaf nodes. **Key: pipe binary doesn't change at any scale.**

Persona registry from federation spec becomes the node registry in a p2p network. Same schema works at every scale: single machine → multiple personas → multiple machines → multi-user network.

### 02:00 - Sandbox Everything + Pipe Multiplexing
User asked about sandboxing all pipes. OS sandbox cost: ~2ms startup, ~0ns runtime (5000x cheaper than WASM). Decision: **sandbox everything, no trusted/untrusted tiers.**

Pipe multiplexing: Mother spawns N instances of same binary with different configs. One pipe binary serves multiple destinations (project, lake, block). Lake-as-source pattern: fetch everything once, project many views. Pipe lifecycle modes: poll (ephemeral), stream (long-lived), manual (one-shot).

Teaching note for a third-year Rust course

Reading patina context like a Rust engineer

This note walks through one real feature, patina context, and asks the question that separates code that works from code a senior would sign off on: what design forces are actually present, and what does the language let you skip? We use the Gang of Four (GoF) pattern catalogue, but mostly as a measuring stick. In Rust the answer is often that a pattern just turns into a language feature, and some of the better decisions in this code don't have a GoF name at all.

Pattern genuinely present Pressure, not yet the pattern Turns into a Rust feature Absent, and correctly so

Start here

The GoF catalogue came out in 1994, written for C++ and Smalltalk. A lot of its twenty-three patterns exist to work around things those languages couldn't do: no first-class functions, no sum types, no ownership, and polymorphism only through inheritance. Rust has those features, so many GoF patterns never become Rust code. They disappear into the language. You use the feature and skip the pattern.

When you catch yourself naming a GoF pattern in Rust, ask a different question first: which language feature already covers this? Most of the time the answer is an enum, a closure, a trait object, or ownership.

We do meet one real pattern in patina context: Facade. But two of the lessons here aren't in the catalogue. One is separating collection from rendering. The other is using types to rule out states that should never exist.

Feature In One Sentence

patina context gathers project orientation data from the knowledge layer, health measurements, factual search, semantic search, and belief search, then exposes that result as either human-readable markdown or structured JSON for child/API callers.

The shape is already visible: collect once into a typed value, then project it. That one boundary is the feature's most important decision, and the rest of this note keeps coming back to it.

What's actually here: Facade

One GoF pattern is clearly present, and it's worth naming because it does real work. get_project_context, get_project_context_report, and collect_project_context put a single call in front of a pile of unrelated subsystems.

Facade present

The caller says "give me context." Behind that one call:

  • layer file reads (layer/core, layer/surface)
  • health measurement (measure)
  • factual keyword search (assay)
  • semantic retrieval (scry / QueryEngine)
  • belief search
  • event logging

This one fits. It cuts the caller's coupling to six subsystems down to a single entry point.

The aggregate that is not Composite

It's tempting to call ContextReport a Composite. It isn't. Composite means leaves and containers share one interface and get handled the same way. ContextReport is a flat record of named fields, and every caller reads those fields by name.

The accurate label is a typed aggregate, or report model (a DTO / view-model). There's pressure toward a uniform section model, but the pattern isn't there yet, and calling it Composite would teach the wrong thing. 

// src/commands/context.rs — the real shape: a record, not a tree.
pub struct ContextReport {
    pub topic: Option<String>,
    pub project_health: Option<ContextHealth>,
    pub core_patterns: Vec<ContextPattern>,
    pub surface_patterns: Vec<ContextPattern>,
    pub factual_matches: Vec<ContextMatch>,
    pub semantic_matches: Vec<ContextMatch>,
    pub beliefs: ContextBeliefs,
    pub recall: RecallDirective,
    pub diagnostics: Vec<String>,   // watch this line
}

Collect first, then render

The biggest improvement in this feature has no GoF name. It's plain separation of concerns: collect the data, then render it.

The markdown string used to be the API. Now ContextReport is the contract, and markdown and JSON are two ways of projecting it.

Before

The feature built one large markdown string. The data shape existed only in the order of push_str calls, so a child tool that wanted the data had to parse prose. 

fn get_project_context(topic) -> String {
    let mut out = String::new();
    if measure_ok() { out += render_health(); }
    out += render_patterns("layer/core");
    out += render_patterns("layer/surface");
    // ... the markdown *is* the API. Yikes.
    out
}

After

Collection returns a typed value. Rendering is a separate function over that value. The same collected data now serves the CLI, child/API JSON, tests, and later Mother orchestration. 

fn get_project_context(topic) -> Result<String> {
    let report = get_project_context_report(topic)?;
    Ok(render_context_markdown(&report))   // projection
}

fn get_project_context_json(topic) -> Result<String> {
    let report = get_project_context_report(topic)?;
    serialize_json(&report)                // another projection
}

This is the move to teach. It isn't Composite or Strategy or any of the twenty-three. It's "make the data a real value, push the formatting to the edge." Good Rust is full of decisions like this that GoF has no words for.

Where the types are too loose

Look again at the last field of ContextReport: 

pub diagnostics: Vec<String>,

This is the clearest sign that the code is correct but not yet finished. A Vec<String> can't tell a fatal condition ("there's no project here, stop") apart from an advisory one ("semantic search was down, but the rest of the report is fine"). The type threw that difference away.

Watch what that forces the renderer to do: 

// src/commands/context.rs — render_context_markdown
if let Some(first) = report.diagnostics.first() {
    return first.clone();   // treat "the first diagnostic" as fatal
}

Because the type can't mark one diagnostic as fatal, the code guesses by position. It assumes the first diagnostic is the show-stopper and returns it as the whole output. That works today only because the one fatal case, "no knowledge layer found," happens to be pushed first and returns early. Add a non-fatal diagnostic ahead of it and the renderer quietly shows the wrong thing. The logic is fine. The type is the problem.

The fix is a type, not a pattern. Give the distinction the domain actually has a name, and the guess-by-position code goes away. The compiler then makes every renderer handle each case. 
enum Diagnostic {
    /// Collection cannot continue; nothing else is meaningful.
    Fatal(FatalReason),
    /// A subsystem was skipped; the rest of the report is still valid.
    Advisory(AdvisoryNote),
}

pub struct ContextReport {
    // ...
    pub diagnostics: Vec<Diagnostic>,
}

// Rendering can no longer guess by position:
match report.diagnostics.iter().find_map(Diagnostic::as_fatal) {
    Some(reason) => render_fatal(reason),
    None => render_full(&report), // advisories shown inline, not as the whole output
}

"Make illegal states unrepresentable" is the Rust principle that quietly does the work a dozen GoF patterns were invented to approximate. If a combination of values should never happen, the strongest design makes it impossible to build, so the compiler enforces it instead of a reviewer.

GoF, read through Rust

Here is the catalogue through Rust eyes. The useful column isn't "used or not." It's what takes the pattern's place when the language is doing its job.

GoF Pattern In patina context What the language does instead
Facade Present Genuinely used: one call over six subsystems. The one GoF pattern that fits here.
Visitor Turns into enum plus exhaustive match. Rust adds operations over a fixed set of variants directly, with no double-dispatch. (See the challenge below.)
Strategy Turns into A closure, an fn pointer, or a small trait. Factual and semantic search are hardcoded today; the day they need to vary, you pass a function.
Command Turns into The CLI enum captures intent; a closure captures deferred work. No execute() interface, no command objects.
State Turns into Type-state, or an enum. The compiler tracks the state machine for you.
Template Method Pressure The fixed collect order (health, patterns, topic search, beliefs) is template-like, but it's a plain function sequence, not inheritance. A list of step functions, not a base class.
Composite Pressure ContextReport is an aggregate, not a Composite. Real uniformity would come from a ContextSection sum type, which is closer to Visitor's stand-in than to Composite.
Adapter Pressure search_beliefs is an adapter-like public boundary over assay's belief FTS. One implementation, so a trait would be needless overhead.
Iterator Built in Rust iterators are used everywhere mechanically; "Iterator" as a design choice is invisible because the language ships it.
Singleton, Abstract Factory, Builder, Factory Method, Prototype Absent No global manager, no families of products, no staged construction worth the overhead. Functions and struct literals are enough. (Singleton is mostly an anti-pattern; reach for OnceLock only if you truly must.)
Bridge, Decorator, Proxy, Flyweight, Chain of Responsibility, Interpreter, Mediator, Memento, Observer Absent None of their forces are present. The topic string is searched, not parsed; logging records usage but notifies no subscribers; nothing wraps, proxies, or shares by reference. Adding any of these would name a problem the feature doesn't have.
Look at the distribution. One row is "present," three are "pressure," several turn into a language feature, and the long tail is simply absent. That spread is the point. In healthy Rust, the GoF catalogue is mostly a list of things you got to skip.

On restraint

A pattern should answer a pressure that is actually there. The thing worth grading isn't how many patterns you can name. It's how few you needed, and whether you can defend each one you kept.

Junior code tends to add structure to look senior: a trait here, a factory there, an interface "for flexibility." Senior code tends to take structure away until only the parts that matter remain. The author of patina context mostly did the second thing: one Facade, a typed report, and a deliberate decision not to abstract the two search paths before there is a third.

What restraint bought

No trait soup. The two search paths read as a plain sequence, and you can hold the whole collect function in your head.

Where it stopped short

The Vec<String> diagnostics and the flat aggregate are where restraint shaded into unfinished. Restraint means skipping needless machinery, not skipping types that describe the domain.

Challenge: make the report a sum type

An earlier draft of this note called this a "Composite" refactor. Wrong pattern. What strengthens the design is a sum type: an enum of section variants with exhaustive rendering. In Rust that's the normal stand-in for GoF's Visitor. A fixed set of variants, with operations defined over them by match. 

enum ContextSection {
    Health(ContextHealth),
    Pattern { layer: PatternLayer, item: ContextPattern },
    Match { source: MatchSource, item: ContextMatch },
    Beliefs(ContextBeliefs),
    Recall(RecallDirective),
    Diagnostic(Diagnostic),   // the typed diagnostic from earlier
}

// Adding a renderer is one new match arm per variant. The compiler
// won't let you forget a section. This is what people wanted from
// Visitor, without the double-dispatch.
fn render(section: &ContextSection, format: OutputFormat) -> String {
    match (section, format) {
        (ContextSection::Health(h), OutputFormat::Markdown) => md_health(h),
        // ... exhaustive, compiler-checked
    }
}

The point of the exercise is to feel the two different "extend" axes. Adding a new section type is easy with the flat aggregate and costly with the enum, since every renderer has to change. Adding a new renderer is the reverse: the enum forces you to handle every section. Which axis you optimise for is the real design decision, not the pattern's name.

Exercise: list every side effect in the current feature (file reads, DB reads, semantic index access, event-log writes, stdout). Then redesign so collection takes its dependencies as parameters and does no I/O of its own. Prove it by testing collect with fake search functions and asserting on the returned ContextReport, no database in sight. 
// Dependencies passed in, so collection becomes testable.
struct ContextEnv {
    layer_root: PathBuf,
    measure: MeasureReader,
    factual_search: Box<dyn Fn(&str) -> Vec<ContextMatch>>,
    semantic_search: Box<dyn Fn(&str) -> Vec<ContextMatch>>,
    belief_search: Box<dyn Fn(&str) -> Vec<ContextMatch>>,
}

fn collect(env: &ContextEnv, request: &ContextRequest) -> ContextReport {
    // pure assembly over env-provided functions; I/O lives at the edge
}

This is dependency inversion, and plain functions satisfy it. No class hierarchy needed. Promote factual_search and friends to a named trait only when a second real implementation needs the same boundary.

What to improve next

Almost none of these are "add a GoF pattern." They are "put the domain in the types" and "keep I/O at the edges."

Improvement The real force Why it helps
Replace diagnostics: Vec<String> with a typed Diagnostic enum (fatal vs. advisory). Make illegal states unrepresentable. The renderer stops guessing by position; the compiler enforces handling of the fatal case.
Pass search and measure dependencies into collect as functions. Dependency inversion. Collection becomes testable with deterministic fakes, no real DB or index.
Keep rusqlite, paths, and file formats at the edges. I/O at the boundary. Domain logic stops depending on storage details and gets easy to unit test.
Move the fixed collect order into an explicit list of step functions. Template Method as data plus functions. Each step is independently testable and reorderable; the order becomes visible.
Add a ContextSection sum type only when sections must be uniform or extensible. Sum type / Visitor stand-in. Renderers gain exhaustive, compiler-checked coverage, paid for only when extensibility is real.

Takeaways

  1. Patterns are workarounds for features a language is missing. In Rust, ask which feature solves the problem before reaching for a GoF name. Often it's an enum, a closure, a trait object, or ownership.
  2. Facade is the one real pattern here, and it fits. Use a pattern when its pressure is genuinely there.
  3. The decisions that mattered most had no GoF name: "collect into a typed value, then render," and "rule out impossible states with types."
  4. A Vec<String> is a warning sign. When a type can hold states the domain forbids, the type isn't doing enough work. Sharpen it and the guessing code disappears.
  5. Restraint is the skill. Most of the catalogue is correctly missing. Knowing which patterns to leave out, and why, is a lot of what "senior" means.

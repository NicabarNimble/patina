# refactor: Data Architecture v2

> Separate immutable history from derived cache, fix emission gaps, align schemas
> across patina.db and mother/graph.db, and expose a rich LLM query surface.

## Problem

### 1. Immutable and derived data share one file

patina.db contains a single `eventlog` table that conflates two fundamentally
different data lifecycles:

**Immutable runtime history** — events generated by tool execution that cannot
be reconstructed from source files:
- `measure.*` — tool metrics over time (scrape, eval, oxidize, bench, audit)
- `forge.*` — cached GitHub API responses (rate-limited, expensive)
- `scry.query/use/feedback` — search feedback loop (user behavior)
- Future: `audit.*` trail

**Derived cache** — events reconstructed from git repo + layer files on disk:
- `code.*` — parsed from source files (58K+ events)
- `git.*` — parsed from git log (5K+ events)
- `pattern.*` — parsed from layer/*.md files
- `session.*` — parsed from layer/sessions/*.md files
- `belief.surface` — parsed from layer/surface/epistemic/beliefs/*.md

Today's `execute_rebuild()` does `std::fs::remove_file(patina.db)` — destroying
both categories. This is a data design error, not a code bug.

At steady state (6 months active use), runtime events grow to ~2,400+:

- ~500+ forge.* from API cache

The 96 events today is a cold-start artifact, not the steady state.

### 3. Schema drift between patina.db and mother/graph.db

Mother's `beliefs` table carries metrics synced from project `beliefs` tables:
`cited_by_beliefs`, `cited_by_sessions`, `applied_in`, `evidence_count`,
`evidence_verified`, `health_score`, `contested_by`. But:

- Mother has no `grounding_score` or grounding breakdown columns
- Mother has no `verification_total/passed/failed/errored` columns
- Mother's `belief_applied_in` table is populated but never queried
- Mother's FTS5 `belief_search` doesn't rank by health_score
- Dangling edges accumulate (71 orphans detected, warning-only)

### 4. Scrape friction blocks automation

Incremental `patina scrape git` takes 15.7s for 5 new commits because
co-change rebuild is O(n²) on 20K+ commit_files. This blocks git hooks.

## Target Architecture

### Principle: Separate by lifecycle, not by size

```
┌─────────────────────────────────────────────────────┐
│  SOURCES (immutable, external — not our databases)  │
│                                                     │
│  .git/               — commits, code, history       │
│  layer/              — patterns, sessions, beliefs  │
│  GitHub API          — issues, PRs                  │
└─────────────────────────────────────────────────────┘
                      ↓
┌─────────────────────────────────────────────────────┐
│  events.db — IMMUTABLE RUNTIME HISTORY              │
│  .patina/local/data/events.db                       │
│                                                     │
│  eventlog table (append-only):                      │
│    measure.*         — tool metrics over time       │
│    forge.*           — cached API responses         │
│    scry.query/use/feedback — search feedback loop   │
│    audit.*           — future audit trail           │
│                                                     │
│  RULES:                                             │
│    - INSERT only. No DELETE. No UPDATE.             │
│    - scrape --rebuild never touches this file       │
│    - Schema: same eventlog columns as today         │
│    - seq is monotonic, timestamp is wallclock       │
└─────────────────────────────────────────────────────┘
                      ↓
┌─────────────────────────────────────────────────────┐
│  patina.db — DERIVED CACHE (rebuildable)            │
│  .patina/local/data/patina.db                       │
│                                                     │
│  eventlog table (mutable cache):                    │
│    code.*, git.*, pattern.*, session.*,             │
│    belief.surface                                   │
│                                                     │
│  30+ materialized view tables                       │
│  5 FTS5 indices                                     │
│  scrape_meta tracking                               │
│                                                     │
│  RULES:                                             │
│    - DELETE+INSERT is correct (cache invalidation)  │
│    - scrape --rebuild = rm + recreate               │
│    - ATTACHes events.db read-only for measure       │
└─────────────────────────────────────────────────────┘
                      ↓
┌─────────────────────────────────────────────────────┐
│  embeddings/ — DERIVED (rebuildable)                │
│  .patina/local/data/embeddings/                     │
│  usearch indices, projection matrices               │
└─────────────────────────────────────────────────────┘
                      ↓
┌─────────────────────────────────────────────────────┐
│  graph.db — FEDERATION INDEX                        │
│  ~/.patina/mother/graph.db                          │
│                                                     │
│  Synced from project patina.dbs + persona values    │
│  Per-source rebuild (failure-safe)                  │
│  Edge weight learning (G2.5 feedback loop)          │
└─────────────────────────────────────────────────────┘
```

### Why this split is correct

The split is by **lifecycle**, not by volume:

- **events.db** will grow indefinitely (append-only). Over 6 months: ~2,400+
  events. Over years: tens of thousands. This is the project's memory.
- **patina.db** is ephemeral. `rm patina.db && patina scrape` should always
  work. It's a cache that accelerates queries.
- **graph.db** is a federation index. Rebuilt from project sources on sync.

The previous audit argued "96 events is too few to justify a split." That
confused current count with architectural intent. The correct framing:
immutable data and disposable cache have different integrity requirements,
regardless of current volume.

## Phase 1: Database Split

### Write-side changes (who writes where)

**Events.db writers** (runtime emissions — small, targeted list):
- `src/measure.rs::emit()` — all measure.* events
- `src/commands/scrape/forge/` — forge.issue, forge.pr events
- `src/commands/scry/internal/logging.rs` — scry.query, scry.use, scry.feedback
- `src/mcp/server/scry.rs` — scry.query, scry.use (MCP path)

**Patina.db writers** (source-derived — no change, same as today):
- All scrape subcommands (code, git, layer, beliefs)
- All materialized view population code
- All FTS5 population code

Implementation: New `eventlog::open_events_db()` function. Writers that emit
runtime events call this instead of opening patina.db. All other code unchanged.

### Read-side changes (who reads what)

**Only `src/commands/measure/internal.rs` needs ATTACH.**

measure is the only command that queries both runtime events AND materialized
tables. It queries `eventlog WHERE event_type LIKE 'measure.%'` and also
reads `beliefs`, `sessions`, etc.

Fix: At the top of `run()`, ATTACH events.db:
```sql
ATTACH DATABASE '.patina/local/data/events.db' AS events READONLY;
```

Then prefix the ~15 eventlog queries: `events.eventlog` instead of `eventlog`.
The materialized table queries (`beliefs`, `commits`, etc.) stay unchanged.

**Other commands don't need ATTACH.** Scry, assay, eval, oxidize all read from
materialized tables in patina.db, not from the eventlog directly.

**Feedback views** (`create_feedback_views()` in eventlog.rs) query scry.query
and git.commit events. These views should move to events.db since they query
runtime events (scry.*) correlated with source-derived events (git.commit).
Alternative: create them as cross-db views with ATTACH.

### Rebuild changes

```rust
// scrape/mod.rs::execute_rebuild()
// Before: rm patina.db (destroys everything)
// After:  rm patina.db only (events.db untouched)

pub fn execute_rebuild() -> Result<()> {
    let db_path = PathBuf::from(database::PATINA_DB);
    // events.db is never touched — it's a separate file
    if db_path.exists() {
        std::fs::remove_file(&db_path)?;
    }
    // Run all scrapers — they recreate patina.db
    // Runtime events in events.db are untouched
    ...
}
```

### Migration

One-time migration on first run after upgrade:
1. Open existing patina.db
2. Copy runtime events to new events.db:
   `INSERT INTO events.eventlog SELECT * FROM eventlog WHERE event_type LIKE 'measure.%' OR event_type LIKE 'forge.%' OR event_type LIKE 'scry.%'`
3. Done. Source-derived events stay in patina.db (they'll be rebuilt on next scrape anyway).

### Files Changed

- `src/eventlog.rs` — add `EVENTS_DB` path constant, `open_events_db()`, migration
- `src/measure.rs` — use `open_events_db()` instead of PATINA_DB
- `src/commands/scrape/mod.rs` — rebuild only touches patina.db
- `src/commands/scrape/forge/` — write forge events to events.db
- `src/commands/scry/internal/logging.rs` — write scry events to events.db
- `src/mcp/server/scry.rs` — write scry events to events.db
- `src/commands/measure/internal.rs` — ATTACH events.db for queries

**7 files.** Not 20+. The earlier audit overestimated because it assumed every
scraper needs changes. Only runtime event *writers* change. Source-derived
scrapers don't touch events.db at all.

### Missing scry event accumulation

scry.query events require `get_active_session_id()` — returns None when no
session is active. This means:

- MCP scry queries during a session: logged (session_id available)
- MCP scry queries outside a session: **not logged**
- CLI scry queries: same behavior

Fix: Log scry.query events even without session_id. Use `session_id: null`
for out-of-session queries. The feedback loop still works — session_id is
only needed for commit-correlation, not for the query record itself.

### Missing session lifecycle emissions

`patina session start` and `patina session end` should emit:
- `measure.evolve` with `tool=session, mode=start` (session_id, branch, goals)
- `measure.evolve` with `tool=session, mode=end` (classification, commits, files)

These go in events.db (runtime events — they record when tools were used).

### Fix: FTS5 ranking

`belief_search` returns pure text relevance. Change `search_beliefs()` to:
```sql
SELECT b.*, rank
FROM belief_search bs
JOIN beliefs b ON bs.id = b.id AND bs.source = b.source
WHERE belief_search MATCH ?1
ORDER BY b.health_score DESC, rank
LIMIT ?2
```

Healthy beliefs surface before unhealthy ones at equal text relevance.

## Design Decisions

### Why split by lifecycle (immutable vs derived)?

Data integrity should be a **construction property**, not a runtime guarantee.
Separate files mean you can't accidentally delete history even with a bug in
rebuild logic. A "protected rebuild" hack (export/restore) depends on the
export code always being correct — one missed WHERE clause and history is gone.

### Why events.db stays small?

events.db only has the eventlog table. No materialized views, no FTS5 indices.
Those are derived data and belong in patina.db. events.db is append-only,
structurally simple, and easy to back up.

### Why only 7 files change?

Source-derived scrapers (code, git, layer, beliefs) write to patina.db — no
change. Only runtime event *emitters* (measure, forge, scry) and the one
*reader* (measure command) need to know about events.db.

### Why fix mother schema now?

Graph sync is already running. The schema drift means cross-project queries
return beliefs without grounding or verification data — making health-based
ranking impossible. Fixing it during the data architecture work is natural
since we're auditing all schemas anyway.

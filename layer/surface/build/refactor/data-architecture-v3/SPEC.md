# refactor: Data Architecture v3 — Provenance and Lake Registry

> Extend data-architecture-v2 with provenance metadata on events and
> lake registry in Mother. Address the external data gap without
> replacing v2's principles.

## Context

**Architecture context:**
- [[session-20260303-190855]] — identified GAP: "external/captured
  data doesn't fit the git + events.db + patina.db model." Forge data
  lives in events.db but it's not "autobiography" — it's observation
  about the outside world. The gap grows when Patina becomes
  domain-agnostic.
- [[session-20260304-120702]] — designed the 4-store conceptual model
  and 4-layer data flow (Sources → Lakes → Modified Data Blocks →
  Projects). Decided: provenance metadata, not physical partition.
- [[events-are-autobiography-not-telemetry]] — events.db is the
  project's autobiography. But external evidence (forge issues, email
  data) isn't autobiography — it's observed evidence. Provenance
  distinguishes them.
- [[content-addressed-references]] — references should be content-
  addressed for portability and future ZK verification.

**data-architecture-v2 (v0.33.1) — read the completed spec:**
```
git show spec/data-architecture-v2:layer/surface/build/refactor/data-architecture-v2/SPEC.md
```
Key principles (all preserved):
- Separate by lifecycle (provenance IS lifecycle metadata)
- Event sourcing (eventlog is still the write model)
- CQRS (events.db writes / patina.db reads)
- Projections are disposable
- Mother is core

## Problem

events.db mixes two fundamentally different kinds of data:

| Kind | Examples | Provenance | Re-creatable? |
|------|----------|-----------|---------------|
| Autobiography | measure.*, session.*, scry.* | local | Only by doing the work again |
| External evidence | forge.issue, forge.pr | external | By re-fetching from API (expensive) |

The split matters because:
1. `scrape --rebuild` should NEVER touch external evidence (re-fetching
   is expensive, rate-limited, and may be impossible if credentials expired)
2. Federation: external evidence may be shared across projects via Mother.
   Autobiography is always project-local.
3. Future: ZK proofs need to distinguish "I observed this" from "I did this"

## Target State

### Provenance on Events (not partition)

Every event carries a `provenance` field in its data payload:

| Provenance | Meaning | Examples |
|------------|---------|----------|
| `local` | Generated by Patina about itself | measure.*, session.*, scry.* |
| `external` | Fetched from external sources | forge.*, connector.* |
| `derived` | Computed from other events | belief.grounded, pattern.detected |

Additive change — existing events without provenance default to `local`.
New connector events carry `external`. The field enables:
- Rebuild safety: `scrape --rebuild` skips external events
- Federation filtering: "share external evidence, not local telemetry"
- Future ZK: different proof types for different provenance

### Lake Registry in Mother

`mother.db → lake_registry` table:

```sql
CREATE TABLE lake_registry (
    name        TEXT PRIMARY KEY,   -- e.g., "github-patina"
    kind        TEXT NOT NULL,      -- "api", "filesystem", "database", "s3"
    location    TEXT NOT NULL,      -- connection string or path
    connector   TEXT,               -- plugin name managing this lake
    credentials TEXT,               -- vault entry reference
    last_sync   TEXT,               -- ISO 8601
    metadata    TEXT                -- JSON: size, records, schema version
);
```

Key properties:
- Lakes are Mother-scoped, not project-scoped
- Multiple projects consume the same lake
- Managed by connector plugins
- Catalogs are cheap (metadata index without full data pull)

### Data Flow

```
SIMPLE (current, valid):   Source → Connector → Project eventlog
FULL (future, for scale):  Source → Connector → Lake → Normalizer → Project
```

The simple path is a degenerate case where the eventlog IS the lake.
[[forge-plugin-extraction]] uses the simple path. Lake infrastructure
is built here but the full pipeline is future work.

## Steps

1. Add `provenance` field to event emission API (new events include it,
   existing events default to `local`)
2. Update `scrape --rebuild` to skip events with `external` provenance
3. Add `lake_registry` table to `mother.db` schema
4. Add `patina lake list` / `patina lake add` commands
5. Update `patina assay` to include lake catalog queries
6. Update `patina doctor` to audit provenance coverage

## Exploration Needed

- **Modified data blocks.** The 4-layer flow includes "Modified Data
  Blocks" (shaped/filtered data between lakes and projects). What are
  these exactly? Structured tables? Semantic embeddings? SQL views?
  This concept needs more design. Could be its own spec. See
  [[session-20260304-120702]] discussion.

- **Lake storage format.** Lakes could be local directories, S3 buckets,
  databases, or API caches. Mother tracks them but doesn't dictate
  format. Should there be a standard lake interface? Or is each
  connector responsible for its own storage?

- **Provenance on existing events.** ~3,500+ events already in
  events.db without provenance. Migration: add provenance column with
  DEFAULT 'local', update forge events to 'external' retroactively?
  Or only apply to new events?

- **Content-addressed event references.** Currently events are
  referenced by seq number. For ZK/federation, content hashes may be
  needed. Should provenance implementation include hash computation?
  **Lean toward: not yet. Add seq-based provenance now. Content
  addressing is a future spec per [[content-addressed-references]].**

## Non-Goals

- **Splitting events.db.** Provenance metadata is sufficient. Physical
  partition is future optimization if volume demands.
- **Building lake sync pipelines.** This spec defines the registry.
  Actual sync is connector plugin work.
- **Migrating existing forge events.** Existing `forge.*` events work.
  New ones carry provenance. Old ones default to `local`.
- **E2EE on lake data.** Future work. See [[content-addressed-references]].

## Relationship to data-architecture-v2

This spec **extends** v2. All 9 principles remain in force:
- P1 (separate by lifecycle) → provenance IS lifecycle metadata
- P2 (event sourcing) → unchanged
- P3 (CQRS) → unchanged
- P4 (projections disposable) → unchanged
- P5 (capture everything) → extended with provenance
- P7 (Mother is core) → extended: Mother manages lakes
- P9 (token-aware) → lake catalogs enable progressive disclosure

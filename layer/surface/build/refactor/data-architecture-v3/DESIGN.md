# Design: Data Architecture v3 — Provenance and Lake Registry

## Relationship to data-architecture-v2

This spec extends v2, not replaces it. [[spec-data-architecture-v2]]
(completed at v0.33.1) established the three-system model:

| System | Store | Role |
|--------|-------|------|
| Declaration | Git (layer/) | Source of truth — beliefs, specs, sessions |
| Event | events.db | Append-only autobiography |
| Projection | patina.db + embeddings/ | Disposable — rebuilt from git + events |

All 9 v2 principles remain in force. v3 adds two things v2 didn't
address: **provenance metadata** on events, and **lake infrastructure**
in Mother.

## The Provenance Problem

events.db currently has 439 events across 12 types. They mix two
fundamentally different kinds of autobiography:

| Source | Event types | Count | Nature |
|--------|-----------|-------|--------|
| Local operations | measure.*, session.*, scry.*, assay.*, context.* | 347 | Things Patina did or observed locally |
| External fetches | forge.issue, forge.pr | 92 | Things Patina observed from the outside world |

Both are autobiography — the project's record of what happened. But
they differ in how they got there and what happens during rebuild:

- `scrape --rebuild` can regenerate local events by re-running scrape
- `scrape --rebuild` CANNOT regenerate external events without
  re-fetching from APIs (expensive, rate-limited, may fail)
- Federation may share external evidence across projects; local
  telemetry stays project-private

The current eventlog schema has no way to express this:

```sql
-- Current schema (no provenance)
CREATE TABLE eventlog (
    seq INTEGER PRIMARY KEY AUTOINCREMENT,
    event_type TEXT NOT NULL,
    timestamp TEXT NOT NULL,
    source_id TEXT NOT NULL,
    source_file TEXT,
    data TEXT NOT NULL,
    CHECK(json_valid(data))
);
```

## Provenance Design

Provenance is metadata, not partition. The eventlog stays as one table.
A new field classifies how each event entered:

| Provenance | Meaning | Examples |
|------------|---------|----------|
| `local` | Generated by Patina about itself | measure.*, session.*, scry.* |
| `external` | Fetched from external sources | forge.*, connector.* |
| `derived` | Computed from other events | belief.grounded, pattern.detected |

**Implementation — two options:**

**Option A: Column on eventlog (additive migration)**
```sql
ALTER TABLE eventlog ADD COLUMN provenance TEXT DEFAULT 'local';
```
- Simple, backward-compatible (existing events default to `local`)
- Queryable: `WHERE provenance = 'external'`
- `scrape --rebuild` adds `WHERE provenance != 'external'` to its
  delete-and-regenerate logic

**Option B: Field in JSON data payload**
```json
{"provenance": "external", "number": 42, "title": "..."}
```
- No schema migration
- Queryable via `json_extract(data, '$.provenance')`
- Consistent with how other metadata lives in the data blob

**Lean toward Option A.** Provenance is a first-class property of
events, not metadata about the payload. It affects rebuild behavior
(a system concern), not just the data shape. A column makes the
rebuild query clean and indexable.

**Migration for existing events:**
- All existing events default to `local`
- Existing `forge.*` events should be updated to `external`
  retroactively — they ARE external evidence
- One-time migration: `UPDATE eventlog SET provenance = 'external'
  WHERE event_type LIKE 'forge.%'`

## Lake Registry

Mother currently manages projects and ref repos via `registry.yaml`.
Lakes extend this pattern — Mother tracks external data sources.

**Current Mother registries:**
- `~/.patina/registry.yaml` — projects (empty) and ref repos (6 repos)
- `~/.patina/graph.db` — federated belief search (nodes, edges, beliefs)

**New: lake_registry in Mother's database.**

The lake registry tracks WHERE external data lives, not the data itself.
Mother is metadata, not storage. Same principle as ref repos — Mother
knows the repo path and synced commit, she doesn't store the code.

```sql
CREATE TABLE lake_registry (
    name        TEXT PRIMARY KEY,   -- e.g., "github-patina"
    kind        TEXT NOT NULL,      -- "api", "filesystem", "database", "s3"
    location    TEXT NOT NULL,      -- connection string or path
    connector   TEXT,               -- plugin name that feeds this lake
    credentials TEXT,               -- vault entry reference (not the secret)
    last_sync   TEXT,               -- ISO 8601
    metadata    TEXT                -- JSON: record count, schema version, etc.
);
```

**Where does this table live?** Two options:
1. **In graph.db** — extend the existing Mother database
2. **In a new lakes.db** — separate concern, separate file

The mother-maturation DESIGN.md open question #5 asks this directly.
**Lean toward graph.db initially** — Mother already has one database
for federation metadata. Adding a table is simpler than a new file.
Separate later if graph.db grows unwieldy.

## Lake Catalog vs Lake Data

A key design principle: Mother stores lake METADATA, not lake DATA.

**Lake catalog** (what Mother knows):
- Name, kind, location, credentials, sync state
- Record counts, schema version, freshness timestamps
- Queryable via `patina assay` — "what lakes exist, when last synced?"

**Lake data** (what connectors manage):
- Actual external data (GitHub issues, email messages, documents)
- Lives at the lake's `location` (local directory, S3 bucket, etc.)
- Flows into project eventlogs via connectors and `host/emit`

This separation means Mother stays lightweight. She's the registry,
not the warehouse. Connectors own the data transport. Projects own
the eventlogs where data lands.

## Data Flow Paths

From [[spec-mother-maturation]] DESIGN.md:

```
SIMPLE (current):  Source → Connector → Project eventlog
FULL (future):     Source → Connector → Lake → Block → Project
```

This spec builds the simple path's provenance tracking and the lake
registry for the full path. It does NOT build the full pipeline —
that's future work once data blocks are designed.

**What the simple path looks like with provenance:**
```
GitHub API → forge connector → emit-fact(provenance=external) → events.db
                                                                   ↓
                                              patina.db projections
                                              (forge_issues, forge_prs)
```

The `provenance=external` tag means `scrape --rebuild` preserves these
events while regenerating local projections.

## Data Blocks — Not This Spec

Data blocks (shaped data between lakes and projects) are acknowledged
in the DESIGN.md but intentionally left open. See [[spec-mother-maturation]]
DESIGN.md, "Data Blocks: Exploration Territory."

What a block could be: structured table, semantic projection, filtered
view, aggregation. The concept needs its own design. May become its own
spec. This spec does NOT define blocks — it builds the infrastructure
(provenance + lake registry) that blocks will eventually sit on.

## Open Questions

1. **Registry format migration.** Mother's project/repo registry is
   YAML (`registry.yaml`). Lake registry is proposed as SQL (graph.db).
   Should the existing registries migrate to SQL too for consistency?
   Or keep YAML for projects/repos and SQL for lakes? **Lean toward:
   keep YAML for now, migrate later if needed.**

2. **Provenance on emit API.** When a connector calls `emit-fact()`,
   does the provenance come from: (a) the emit call parameters, (b)
   the plugin's role (connectors are always external), or (c) explicit
   per-event declaration? Option (b) is simplest — if role=connector,
   host sets provenance=external automatically. But a connector might
   emit derived facts too.

3. **Assay integration for lakes.** EC4 says lake metadata is queryable
   via `patina assay`. Does assay grow a new query_type (`lakes`)?
   Or does `assay search` index lake metadata alongside code and
   commits? **Lean toward: new query_type.** Lake queries are
   structural (list, filter), not text search.

4. **Rebuild safety testing.** How to verify EC2 (external evidence
   survives rebuild) in CI? Need a test that: inserts external events,
   runs `scrape --rebuild`, verifies external events survive while
   local projections are regenerated. Integration test required.

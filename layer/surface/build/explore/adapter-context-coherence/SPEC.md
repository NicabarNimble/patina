# explore: Adapter Context Coherence

> Patina has three injection channels into LLM adapters — MCP (live), bootstrap
> files (stale), and skills (Claude-only). Only MCP stays current. The bootstrap
> file rots from the moment it's generated. Skills don't exist outside Claude.
> The user becomes the drift-correction mechanism, manually nudging adapters to
> use the right tools and follow the right workflows. This defeats Patina's
> primary mission: being the accurate context reboot layer.

## Problem

### Three channels, one healthy

| Channel | Mechanism | Freshness | Adapter coverage |
|---------|-----------|-----------|-----------------|
| **MCP tools** | scry, context, assay — live queries | Always current | All 3 adapters |
| **Bootstrap file** | CLAUDE.md / GEMINI.md / OPENCODE.md | Generated once at `patina init` | All 3 (different files) |
| **Skills** | `.claude/skills/` SKILL.md files | Manual refresh | Claude only |

MCP is stateless and always current — it's the healthiest channel. But adapters
need *ambient* context at session start (project patterns, workflow guidance,
active specs) that MCP can't provide until the LLM knows to call it. The
bootstrap file is supposed to bridge this gap, but today `patina_section()`
generates a 4-line stub:

```markdown
<!-- PATINA:START -->
## Patina

MCP tools: `scry` (search), `context` (patterns)

*Generated by Patina | Adapter: Claude Code*
<!-- PATINA:END -->
```

Everything useful in CLAUDE.md (build recipe, git discipline, spec commands,
testing guidelines) is hand-written above the markers. Patina doesn't own it,
doesn't refresh it, can't detect when it's stale.

### Skills divergence

Session workflows (`/session-start`, `/session-update`, `/session-end`) and
belief capture (`/epistemic-beliefs`) exist as Claude skill files. Gemini and
OpenCode have nothing — they get the stub bootstrap and MCP tools, that's it.
The user must manually explain session workflow to non-Claude adapters every
session.

### Multi-project confusion

Each project has its own bootstrap file. But Patina knowledge is two layers:
- **Global**: "What is Patina, how do tools work, what are my persona beliefs"
- **Project**: "What are this project's patterns, active specs, build recipe"

Today, CLAUDE.md mixes both. Global Patina knowledge is copy-pasted into every
project's bootstrap file. When Patina evolves, every project's file is stale.

## Exploration Questions

### 1. Can we converge on AGENTS.md?

The codebase already maps `"codex" => "AGENTS.md"` (`src/adapters/launch.rs:325`).
Claude Code reads both CLAUDE.md and AGENTS.md. The AGENTS.md format is gaining
adoption as the universal agent context file.

**Question:** Can AGENTS.md replace all three adapter-specific files?

- Claude reads AGENTS.md (confirmed)
- Gemini reads GEMINI.md — does it read AGENTS.md?
- OpenCode reads OPENCODE.md — does it read AGENTS.md?
- What happens when both CLAUDE.md and AGENTS.md exist?

**If yes:** One file to maintain, one file to refresh, one file to keep current.
Adapter-specific files become thin shims or disappear entirely.

**If no:** The marker system (`<!-- PATINA:START/END -->`) works across all files.
Patina generates the same rich section into whichever file each adapter reads.

### 2. What should the Patina section contain?

Today: 4 lines. Should be: rich, live, progressive.

**Candidate content (generated from project state):**

```markdown
<!-- PATINA:START -->
## Patina

### MCP Tools
- `scry` — semantic search over code, commits, beliefs
- `context` — project patterns and conventions (USE before architectural changes)
- `assay` — structural queries (imports, callers, co-change)

### Active Specs
- [[plugin-template-gallery]] (design) — Plugin scaffolding
- [[cli-reorganization]] (design) — CLI restructure

### Session Workflow
- `/session-start <name>` — begin tracked session
- `/session-update` — capture progress checkpoint
- `/session-note <insight>` — record insight
- `/session-end` — archive and distill learnings

### Key Beliefs (top 5 by entrenchment)
- [[spec-driven-design]] — specs authorize action
- [[stale-context-is-hostile-context]] — obsolete context misdirects
- [[compiler-enforced-safety]] — enums over strings
- [[sync-first]] — no async infection
- [[mcp-is-shim-cli-is-product]] — CLI is the product

### Build & Test
```
cargo build --release && cargo install --path .
./resources/git/pre-push-checks.sh
```

*Generated by Patina v0.21.1 | 2026-02-14 | 109 beliefs indexed*
<!-- PATINA:END -->
```

**Key principle:** [[progressive-disclosure]]. The bootstrap section gives enough
context to orient the LLM and point it toward MCP tools for deeper queries. It
doesn't dump the entire knowledge base — it provides the map, not the territory.

### 3. When should the section refresh?

Options (not mutually exclusive):

| Trigger | Mechanism | Freshness |
|---------|-----------|-----------|
| `patina adapter refresh` | Manual CLI command | On-demand |
| `patina scrape` | After reindexing | Post-scrape |
| `patina session start` | At session boundary | Per-session |
| Git hook (post-commit) | Automatic | Per-commit |
| Mother daemon | Watch for layer changes | Real-time |

The per-session trigger seems right: refresh the bootstrap at session start,
when the LLM is about to reboot context. This is when staleness hurts most.

### 4. Global vs project context split

Two Patina sections, different sources:

**Global** (`~/.patina/` or user-level AGENTS.md):
- What is Patina (protocol overview)
- How to use MCP tools
- Session workflow commands
- User persona beliefs
- Cross-project patterns

**Project** (repo-level AGENTS.md):
- Active specs and their status
- Project-specific patterns and beliefs
- Build recipe
- Testing guidelines
- Key architectural decisions

**Question:** Should the bootstrap file contain both? Or should global context
live in a user-level config file that adapters read automatically?

Claude Code supports `~/.claude/CLAUDE.md` for global instructions. If all
adapters support a global config, the split becomes:
- Global file: Patina workflow knowledge (same everywhere)
- Project file: Project-specific knowledge (varies per repo)

### 5. Where do skills fit?

The [[skills-focused-adapter]] spec (design) proposes universal SKILL.md format
across all three adapters. The Agent Skills specification (agentskills.io) is
the emerging standard. Skills are the structured workflow channel:

- **MCP tools** = "Here's data" (query-response)
- **Skills** = "Here's how to do X" (workflow template)
- **Bootstrap** = "Here's who you are in this project" (ambient context)

Skills solve the workflow divergence problem — session commands, belief capture,
spec management as portable skill definitions rather than adapter-specific files.

**Question:** Can skills replace the workflow sections in the bootstrap file?
If the adapter discovers skills automatically, the bootstrap only needs to
provide project identity and point to MCP tools. Skills handle the "how."

### 6. Can the plugin system help?

Per [[patina-identity]], the protocol test:

- Is adapter context generation a protocol operation? No — it's not capture,
  index, search, believe, or evolve.
- Does it use the protocol? Yes — it reads patterns, beliefs, specs from the DB.
- Is it infrastructure? No — it doesn't need full host access.

**Verdict:** Protocol tooling. Compiled today, extractable later. The pipeline
plugin world (pure compute: input data, output text) is the natural extraction
target. But this doesn't need to be a plugin to solve the immediate problem —
enriching `patina_section()` in `launch.rs` is the first step.

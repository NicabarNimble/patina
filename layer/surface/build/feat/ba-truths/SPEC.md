# feat: BA Truths Foundation

## Problem

Patina is making a public bet that the Bytecode Alliance's direction — WASM
component model, WIT, WAC, WASI preview 2 → 3 — is the substrate for "correct
by construction" software. To honor that bet, MCT must stay aligned with BA's
actual current direction, not a historical snapshot.

The current `sdk/ba/repos.toml` is hand-curated. Hand-curation has three
problems:

1. **Goes stale fast.** BA pivots, new proposals appear, old proposals get
   merged or archived. A static list rots within weeks.
2. **Captures inventory, not intent.** A list of repos doesn't tell us what
   BA is *pushing toward*. We need themes, not just URLs.
3. **Misses the ecosystem.** BA's direction is also advanced by projects
   *outside* BA — Spin (Fermyon), wasmCloud, Extism, Wick. These need
   tracking even though they're not under the bytecodealliance org.

We need a process that produces and maintains the alignment, not a static
artifact.

## Goal

Build a skill-driven foundation that:

1. **Discovers BA's current direction** — themes, active proposals, recent
   decisions — by reading authoritative BA sources
2. **Generates `repos.toml`** as a derived artifact from the direction
   analysis, not as a hand-curated list
3. **Tracks ecosystem projects** that advance the CM/WASI direction (BA or
   not)
4. **Maintains a counter-observations list** of projects that diverge from
   BA so we understand the alternatives
5. **Runs manually** until the output is trusted, then can be re-run on
   demand whenever direction shifts

The skill is the durable artifact. `DIRECTION.md` is its output. `repos.toml`
is generated from `DIRECTION.md`. Everything traces to a theme.

## Non-Goals

- **Automation.** No cron, no scheduled runs, no hooks. Manual invocation
  only until the output is verified trustworthy. Automation is a separate
  spec when the time comes.
- **Parallel knowledge storage.** Use Patina's existing repo system
  (`patina repo add` → `~/.patina/cache/repos/`), belief system, and git.
  No new database, no new format.
- **Tracking everything in WASM.** Tight scope: component model + WASI +
  ecosystem projects advancing them. WASM core spec, preview1, browser
  WASM, historical proposals — all out of scope or low priority.
- **Live BA fork.** We do not maintain copies of BA work. We link, summarize,
  and capture insight as beliefs.

## Architecture

### File Structure

```
sdk/ba/
├── README.md                       # orientation (updated by bt5)
├── DIRECTION.md                    # current snapshot (generated by skill)
├── COUNTER-OBSERVATIONS.md         # diverging projects, observation-only list
├── repos.toml                      # generated from DIRECTION.md
├── skills/
│   └── discover-direction.md       # the skill spec
└── scripts/
    └── add-all.sh                  # registers repos.toml entries (already exists)
```

### The Production Chain

```
discover-direction.md (skill spec)
        │
        │ runs manually via any LLM
        ↓
DIRECTION.md (current snapshot)
        │
        │ extract repo list per theme
        ↓
repos.toml (generated)
        │
        │ add-all.sh
        ↓
patina repo add → ~/.patina/cache/repos/
        │
        │ patina scry / assay / direct read
        ↓
beliefs (capture insight, ground Patina decisions)
```

### Skill Spec Contents

`sdk/ba/skills/discover-direction.md` defines:

1. **Mission** — what the skill produces and why
2. **Source funnel discovery** — how to find where BA direction lives (blog,
   meetings, RFCs, code, talks). First run discovers; later runs verify
   funnel still current.
3. **Source list** — initial seed list of canonical sources to fetch
4. **Theme extraction rules** — what counts as a theme (concept appearing
   in 3+ independent sources within last N days)
5. **Scope filter** — HIGH / MEDIUM / LOWER / DROP rules
6. **Output format** — DIRECTION.md structure (themes, repos, decisions,
   emerging, stagnant, counter-observations, sources used)
7. **repos.toml generation rules** — how to derive entries from themes
8. **Stop rules** — when to halt (avoid runaway exploration)
9. **Verification questions** — what the human reviewer should sanity-check

The skill spec is portable across all 4 interfaces (Claude, OpenCode,
Gemini, Pi). Interface-specific wrappers can be added later as thin pointers
to the spec.

### DIRECTION.md Structure

Sections:

- **Generated**: date and which LLM produced it
- **Sources Used**: the funnel — which authoritative sources were fetched
- **Themes**: BA's current focus areas, each with description and why it matters
- **Active Repos by Theme**: which repos serve which theme, with relevance
- **Recent Decisions**: from meeting notes, RFCs (last ~90 days)
- **Emerging**: new proposals or work that wasn't here last snapshot
- **Stagnant**: things BA used to push that are now dormant
- **Counter-Observations**: brief mention; details in COUNTER-OBSERVATIONS.md
- **Open Questions**: things the skill couldn't determine, flagged for human

### COUNTER-OBSERVATIONS.md

A list, not a tracked-repo set. Each entry:

- Project name + URL
- One-line summary of what it does
- How it diverges from BA direction
- Why it matters (alternative model? competing standard? niche use case?)
- Last verified date

Wasmer is the canonical example: alternative WASM runtime, history of
divergence with BA, useful as a counter-observation point. We do not
`patina repo add` Wasmer — we observe it from a distance.

### Scope Filter

| Tier | What | Track? |
|------|------|--------|
| **HIGH** | Component model, WASI proposals, BA host/tooling for CM/WASI, ecosystem projects (Spin, wasmCloud, Extism, Wick) advancing CM/WASI | Yes, register in patina repo |
| **MEDIUM** | BA tooling supporting CM/WASI workflows (cargo-component, wasm-pkg-tools, wrpc) | Yes, register |
| **LOWER** | WASM core spec, preview1 historical, peripheral BA tools | Yes, register but mark low |
| **DROP** | Browser WASM, JS-VM-only WASM, orthogonal proposals, archived/dead | No, do not register |
| **COUNTER** | Wasmer and other diverging projects | No, list only in COUNTER-OBSERVATIONS.md |

## Implementation Order

1. **Update `sdk/ba/README.md`** to describe the new structure (DIRECTION.md
   primary, repos.toml generated, skill as producer, counter-observations as
   list). Mark current `repos.toml` as transitional. (bt5)
2. **Write `sdk/ba/skills/discover-direction.md`** — the skill spec, complete
   and self-contained. (bt1, bt9, bt10)
3. **Run the skill manually** with an LLM agent (likely Claude as primary
   first) to produce the first `DIRECTION.md`. Includes funnel discovery. (bt2, bt6)
4. **Generate `repos.toml`** from DIRECTION.md analysis. Each entry traces to
   a theme. Replaces the hand-curated list. (bt3)
5. **Write `sdk/ba/COUNTER-OBSERVATIONS.md`** with Wasmer as the first entry.
   Future counter-observations get added as discovered. (bt4)
6. **Run `add-all.sh`** to register the canonical repo set in Patina's repo
   system. (bt7)
7. **Write at least one alignment belief** that cites a BA fact and grounds
   a Patina decision. Sets the `ba-aligns-*` / `ba-extends-*` / `ba-diverges-*`
   pattern. (bt8)

## Resolved Decisions

- **Skill location**: `sdk/ba/skills/discover-direction.md`. Portable
  markdown spec, single source of truth across all 4 interfaces.
- **Snapshot storage**: single `DIRECTION.md` file, updated in place. Git
  history is the snapshot history. No dated files.
- **Repos source of truth**: `repos.toml` is generated from `DIRECTION.md`.
  Hand-edits to `repos.toml` are forbidden — they get blown away on
  regeneration. Add the repo to the right theme in DIRECTION.md instead.
- **Counter-observations**: list with notes, not Patina repos. We observe
  divergent projects without polluting the canonical knowledge index.
- **Manual runs only**: no automation until trust is established. Period.
- **Scope is tight**: CM + WASI + ecosystem advancing them. Everything else
  is lower priority or out of scope.
- **The skill discovers the funnel**: hardcoding the source list defeats the
  purpose. The skill must find authoritative sources and update the funnel
  itself across runs.
- **No new storage**: use `patina repo`, beliefs, git-tracked markdown.
  Anything else requires explicit justification.

## Verification

```bash
# Skill spec exists and is non-empty:
test -s sdk/ba/skills/discover-direction.md

# DIRECTION.md generated:
test -s sdk/ba/DIRECTION.md
grep -q "## Themes" sdk/ba/DIRECTION.md
grep -q "## Sources Used" sdk/ba/DIRECTION.md

# Counter-observations exists with at least one entry:
test -s sdk/ba/COUNTER-OBSERVATIONS.md
grep -qi "wasmer" sdk/ba/COUNTER-OBSERVATIONS.md

# repos.toml regenerated, traces to themes:
grep -q "theme = " sdk/ba/repos.toml

# All canonical repos registered:
sdk/ba/scripts/add-all.sh --dry-run | grep -c "skip"
# ^ should equal the count of entries in repos.toml

# At least one alignment belief exists:
ls layer/surface/epistemic/beliefs/ba-{aligns,extends,diverges}-*.md 2>/dev/null \
  | head -1

# README reflects new structure:
grep -q "DIRECTION.md" sdk/ba/README.md
grep -q "COUNTER-OBSERVATIONS.md" sdk/ba/README.md
```

## Build Readiness

- `patina repo add` already clones, scrapes, oxidizes external repos
- `~/.patina/cache/repos/` is the canonical cache location
- `patina scry` and `patina assay` already query indexed repos
- Belief system is in place for capturing alignment insights
- `sdk/ba/scripts/add-all.sh` already registers from `repos.toml`
- Initial `sdk/ba/README.md` and `repos.toml` exist as transitional artifacts

The new work: skill spec, first run, regenerated artifacts, counter-observations
list, README update, first alignment belief.

## Open Questions for Future Specs

- **When to automate?** After how many successful manual runs do we trust
  the skill enough to schedule it? What's the verification gate?
- **How to handle BA pivots?** When DIRECTION.md changes substantially,
  do we open a Patina spec to react? A belief? A note in the session log?
- **Multi-LLM parity?** If Claude and Gemini produce different DIRECTION.md
  outputs from the same skill spec, which is canonical? Diff and reconcile?
- **Scaling counter-observations?** If the list grows past ~10 projects,
  does it become its own skill (`discover-counter-observations`)?
